# Genesis Garden — экономика и баланс

## Источники правды

Баланс существует в двух местах, которые должны совпадать:

1. **Клиент (офлайн-демо / пока не подключён к Supabase):** `apps/web/src/game/config.ts` — единая конфигурация, см. Этап 2. `GameStore` использует её напрямую, ничего не гарантирует сервер.
2. **Сервер (авторитетный, Этап 3):** захардкожен внутри SQL-функций `supabase/migrations/20260827120200_functions.sql` (константы вроде `v_breed_cost`, пулы генов в `breed()`/`random_genome()`, формула `expand_plot()`) и таблиц `seed_catalog`/`quests` (наполняются миграцией `20260827120300_catalog_data.sql`).

**При изменении любого числа баланса — менять оба места.** Тест на совпадение сумм (например, `test-e2e-genetics.mjs` для клиента и `supabase/tests/02_scenario_tests.sql` для сервера) ловит расхождение только косвенно (через ассерты внутри своей стороны), не автоматическим диффом между TS и SQL. Это осознанный компромисс MVP; кандидат на улучшение — таблица `game_config` в БД, которую читают и клиент (через публичный RPC), и сами SQL-функции, чтобы было ровно одно место правды. Не сделано в Этапе 3 из-за ограниченного времени, зафиксировано как технический долг.

## Список зеркалируемых констант (клиент -> сервер)

| Параметр | Клиент (`config.ts`) | Сервер (SQL) |
|---|---|---|
| Стоимость разблокировки грядки | `GARDEN_CONFIG.unlockCostBase=20`, `.unlockCostStep=12`, `.startUnlockedPlots=6` | `expand_plot()`: `20 + greatest(plot_index-6,0)*12` |
| Стоимость скрещивания | `BREEDING_CONFIG.breedCost=12` | `breed()`: `v_breed_cost=12` |
| Награда пылью за скрещивание | `dustRewardMin=2`, `dustRewardMax=5` | `breed()`: `v_dust_min/max` |
| Награда пылью за переработку | — (клиент пока продаёт за 15 монет, `sellSpecimenValue`; см. ниже) | `recycle_plant()`: `v_dust_reward=5` |
| Пороги/шансы генетики | `GENETICS_CONFIG.*` | `breed()`/`random_genome()`, константы с теми же именами в комментариях |
| Очки редкости | `RARITY_SCORING.*` | `rarity_of()` |
| Потолок ускорения роста | `BOOSTS_CONFIG.maxTotalGrowthBoostPercent=0.25` | `active_growth_boost_percent()`: `least(sum, 0.25)` |
| Семена (цена/таймер/продажа) | `SEED_BALANCE[]` | таблица `seed_catalog` (заполнена migration 20260827120300) |
| Квесты | `QUEST_CATALOG[]` | таблица `quests` (та же миграция) |

## Сознательное расхождение: recycle vs sell

Текущий клиент (`AlbumPanel.tsx` → `gameStore.sellSpecimen()`) продаёт лишний специмен за **монеты** (15 шт, `BREEDING_CONFIG.sellSpecimenValue`). Мастер-промт для Этапа 5 требует другого: «ненужное растение превращается в генетическую пыль». Серверная функция `recycle_plant()` уже реализована по целевой механике (даёт **пыль**, не монеты) — это специально сделано на Этапе 3 вперёд, чтобы не переделывать backend в Этапе 5. Client-side переключение `AlbumPanel` с «продать за монеты» на «переработать в пыль» — задача Этапа 5, зафиксирована в `docs/IMPLEMENTATION_STATUS.md`. Пока клиент работает в офлайн-демо режиме (без Supabase), обе механики физически не конфликтуют — путаницы для игрока это не создаёт, т.к. Этап 4 ещё не подключил клиент к серверным RPC.

## Лимиты монетизации (Этап 7, справочно)

- Суммарное ускорение роста ≤ 25% (см. `BOOSTS_CONFIG`/`active_growth_boost_percent()`).
- Платежи не влияют на шанс редкости — `breed()` не принимает и не проверяет никакие платёжные данные вообще.
- Дневной лимит подарков: 5 (константа `v_daily_limit` в `send_gift()`) — предварительное значение, владелец может попросить изменить перед бетой.

## Идемпотентность и деньги

Каждая изменяющая RPC-функция (`plant`/`harvest`/`buy_seed`/`expand_plot`/`breed`/`recycle_plant`/`claim_quest`/`send_gift`/`claim_gift`/`decline_gift`/`grant_purchase`) защищена таблицей `request_log`: клиент передаёт `request_id` (UUID, генерируется один раз на попытку действия и переиспользуется при retry); функция сначала пытается атомарно вставить строку в `request_log` — если конфликт (запрос уже был выполнен и закоммичен), возвращается сохранённый ответ без повторного выполнения логики. Если валидация внутри функции проваливается, вся транзакция (включая вставку в `request_log`) откатывается — то есть один и тот же `request_id` можно безопасно повторить позже, когда условие изменится (растение созреет, баланс пополнится). Подробности и живые тесты — `supabase/tests/02_scenario_tests.sql`.
