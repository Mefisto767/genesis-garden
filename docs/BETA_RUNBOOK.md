# Genesis Garden — раннбук закрытой беты

Практическое руководство для запуска и сопровождения закрытой беты (50–100 живых игроков). Не дублирует архитектурные детали — за ними см. `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/DEPLOYMENT.md`.

## Два варианта запуска беты

### Вариант A — без облака (готово сейчас, ничего дополнительно настраивать не нужно)

Бета-тестер открывает `https://mefisto767.github.io/genesis-garden/` (после того как деплой обновится через CI/CD, см. `docs/DEPLOYMENT.md`) и играет полностью локально: прогресс в `localStorage` браузера, без аккаунта, без сервера. Подходит для проверки геймплея/баланса/арта, но: прогресс не переживает смену устройства/браузера, нет соцобмена и покупок (они требуют облачного аккаунта), нет данных для admin-дашборда.

Этот вариант работает уже сегодня без единого действия владельца.

### Вариант B — с облаком (аккаунты, соцобмен, покупки, аналитика)

Требует реального Supabase-проекта. Пошагово:

1. **Создать проект Supabase** (supabase.com, бесплатный tier достаточен для 50–100 игроков на старте).
2. **Прогнать миграции**: `supabase/migrations/*.sql` по порядку (имена файлов уже отсортированы по времени — можно просто по очереди выполнить их через Supabase SQL Editor, либо через `supabase db push`, если будет установлен Supabase CLI). Файлы идемпотентны в применении по порядку один раз; повторный прогон **не** предусмотрен (не `CREATE IF NOT EXISTS` везде) — на чистом проекте только один раз.
3. **Получить ключи**: Project Settings → API → `URL` и `anon public key`.
4. **Настроить `.env.local`** в `apps/web` (см. `apps/web/.env.example`):
   ```
   VITE_SUPABASE_URL=<твой project URL>
   VITE_SUPABASE_ANON_KEY=<твой anon key>
   VITE_CLOUD_SYNC_ENABLED=true
   ```
5. **Пересобрать и задеплоить** (`docs/DEPLOYMENT.md`) — если хочешь включить это по умолчанию для всех, эти значения нужно завести как GitHub Actions repo secrets и прокинуть в шаг `Build` workflow (сейчас туда намеренно не прокинуты, см. комментарий в начале `.github/workflows/ci.yml`).
6. **Проверить Auth-настройки Supabase**: Authentication → Providers → Email должен быть включён (magic link — единственный рабочий способ входа сейчас, см. `docs/MASTER_PLAN.md`, OAuth — задокументированное расширение на будущее, не реализовано).
7. **Настроить Site URL / Redirect URLs** в Authentication → URL Configuration на реальный адрес GitHub Pages — иначе magic link будет редиректить не туда.

Ничего из этого не проверено вживую этой сессией разработки (нет доступа к реальному Supabase-проекту) — весь серверный код проверен через локальный SQL-шим, имитирующий Supabase (см. `docs/ARCHITECTURE.md`, раздел «Тестовая инфраструктура»). Первое реальное включение — ответственность владельца, шаги выше описывают ожидаемый путь, а не гарантированно безошибочный.

## Как выдать первому админу доступ к дашборду

После того как нужный человек хотя бы раз вошёл в игру (появилась строка в `profiles`):

```sql
update public.profiles set is_admin = true where id = '<uuid игрока>';
```

`uuid` — это `id` в `auth.users`/`profiles` (Supabase Dashboard → Authentication → Users, либо `select id, public_code from public.profiles;`). Кнопка «Admin» появится в HUD у этого игрока после следующего входа. Подробности дашборда — `docs/ANALYTICS.md`.

## Перед стартом беты — чек-лист

- [ ] `VITE_PAYMENTS_PROVIDER` — **не** `mock` в проде, если реально включаешь покупки (иначе бета-тестеры «купят» что угодно бесплатно, см. `docs/PAYMENTS.md`). Если Paddle-аккаунта ещё нет — держи `VITE_PAYMENTS_ENABLED=false`, покупки в UI не появятся вообще.
- [ ] `VITE_SENTRY_DSN` — если хочешь получать отчёты об ошибках от бета-тестеров, заведи проект в Sentry и укажи DSN. Без него — приложение работает штатно, просто ошибки никуда не репортятся, кроме консоли игрока.
- [ ] Прогнать полный набор тестов (`docs/TESTING.md`) на актуальном коммите перед объявлением о старте.
- [ ] Проверить, что деплой на GitHub Pages актуален (Pages API/просто открыть сайт и свериться с последним коммитом).
- [ ] Если включаешь облако — пройти сценарий 2 из `docs/TESTING.md` (перенос локального сейва) вручную самому один раз перед тем, как давать доступ бета-тестерам с уже накопленным локальным прогрессом.

## Типовые инциденты и что делать

**Бета-тестер потерял прогресс.** Если играл без облака — прогресс живёт только в его `localStorage`, восстановить нельзя (это ожидаемое поведение локального режима, не баг). Если играл с облаком — прогресс в Supabase `gardens`/`plants`/... по `owner_id`/`garden_id`, можно посмотреть напрямую через SQL Editor; удаления из UI нет ни у одной операции, кроме `recycle_plant` (специмен) — потеря прогресса через баг маловероятна, но если случилась, `economy_ledger` хранит аудит каждого изменения монет/пыли для расследования.

**Подозрение на дублирование награды/двойную трату.** Все изменяющие RPC идемпотентны по `request_id` через `request_log` (см. `docs/ARCHITECTURE.md`) — посмотри `select * from request_log where garden_id = '<uuid>' order by created_at desc;`, чтобы увидеть, был ли повторный вызов с тем же `request_id` (ожидаемо — не должен был исполниться дважды) или с разными (два реальных отдельных вызова — не баг идемпотентности, а вопрос к клиентской логике/лимитам).

**Под подозрением абьюз соцобмена.** `block_user`/`unblock_user` доступны игроку из `SocialPanel.tsx` — это решает обычные конфликты между двумя игроками. Полного бана аккаунта администратором пока нет: колонка `profiles.banned` существует в схеме и защищена от самостоятельного изменения игроком (триггер в `20260827120100_rls.sql` откатывает попытку `authenticated` поменять её самому), но ни RLS, ни одна из игровых RPC сейчас **не проверяет** значение `banned` — установка `banned = true` вручную через SQL пока ничего не заблокирует по факту. Это честно зафиксированный пробел, не готовая функция бана: реальный инструмент модерации для беты — просьба удалить/деактивировать пользователя на уровне Supabase Auth (Authentication → Users → Delete/Ban), это уже сработает по-настоящему.

**CI упал на шаге деплоя, но тесты зелёные.** Смотри `docs/DEPLOYMENT.md` — известные заранее непроверенные места (реальный GitHub Actions раннер никогда не запускал этот workflow из этой сессии разработки).

## Сбор обратной связи

В проекте нет встроенной формы обратной связи (не было в ТЗ). Рекомендуемый минимум для 50–100 тестеров: отдельный Discord/Telegram-канал + периодический экспорт `analytics_events`/admin-дашборда для количественной картины (retention, воронка первого скрещивания, доход — уже считаются, см. `docs/ANALYTICS.md`).
