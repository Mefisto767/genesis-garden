## 0. Что изменилось в этом проходе (changelog)

Владелец зафиксировал развилки, которые в проходе 1 были перечислены как «вопросы, которые невозможно решить по коду и документам» (§9 предыдущей версии). Закрыто явным решением владельца (было открытым вопросом в проходе 1):
1. Политика миграции скрытых аллелей — **гомозиготность**, без случайной генерации (было вопросом №1).
2. Стартовый грант пыльцы при миграции — **условный**: 24 для save с историей скрещиваний, 0 для нетронутого (было вопросом №2).
3. Дефолтный Lab-уровень при миграции — **условный**: 3 для save с историей, 1 для нетронутого (было вопросом №3).
4. Обязательность Nursery Tray для Gate 1 — **обязателен**, включая посадку и выращивание в E2E (было вопросом №4).
5. Судьба текущих 4 mutation ID — **сохраняются и классифицируются** по тирам, плюс 2 новых временных ID (было вопросом №5).
6. Поведение при заполненном Nursery Tray — **скрещивание блокируется** до освобождения слота, с явным UI-текстом (было вопросом №6).
7. Судьба SQL-порта — **заморожен**, не обновляется в Gate 1 (было вопросом №7).
8. Комбинации фича-флагов — **не 4 независимые**, а один зависимый флаг: Genetics V2 требует одновременно оба флага, Classic UI всегда на legacy (было вопросом №8).
9. Переходное состояние геометрических локусов у species 3-8 — снято тем, что **эти виды нельзя использовать как родителей V2 до реализации их локусов** (было вопросом №9).

Новые уточнения, добавленные в этом проходе сверх прямых решений владельца, помечены отдельно как «вывод из зафиксированных решений» — это логические следствия, которые нужны, чтобы решения были реализуемы, но не были продиктованы дословно. Они помечены по месту и собраны в §11.

### 0.2. Consistency-lock pass (проход 4) — устранённые межфайловые противоречия

Владелец провёл межфайловую проверку `GENETICS_TARGET_DELTA.md`, `GENETICS_ONBOARDING_SPEC.md`, `genesis-garden-core-game-gdd-v3.md` и `genesis-garden-balance-model-v3.xlsx` и обнаружил девять групп продуктовых противоречий между ними. 15. **Микроскоп противоречил расширенной карточке.** Расширенная карточка бесплатно показывала оба аллеля и полный список скрытых признаков — обесценивая платное раскрытие микроскопом. Зафиксирован единый контракт видимости генетики: простая карточка показывает только выраженный фенотип; расширенная карточка без исследования показывает выраженный аллель, второй — как «Не исследован»; точное значение и доминирование скрытого аллеля показываются только после раскрытия микроскопом за 3 пыли **или** после того, как этот же скрытый аллель фактически проявился у потомка на Reveal (естественное раскрытие). ### 0.4. Проход 5 — исправление технических дефектов и одного незакрытого блока (QA перед Gate 0)

Финальная проверка перед принятием Gate 0 нашла четыре конкретных дефекта в документах прохода 4 — три технических формулировки и один незакрытый содержательный блок (переход на 9-локусную модель). Ни один из них не является новой продуктовой развилкой — все четыре укладываются в уже принятые решения владельца, это исправление формулировок/пробелов, не новые решения.

1. **Slice 6 (§12) ошибочно описывал бесплатность первого скрещивания как «расширение `isFirstBreedAttempt`»**, хотя §5.1/§6.2 этого же документа уже правильно фиксировали, что источник истины — персистентное поле `GameState.firstBreedFreeClaimed`, а `isFirstBreedAttempt()`/`markBreedAttempted()` (`localStorage`) — чисто аналитический сигнал. Формулировка Slice 6 приведена в соответствие: бесплатность определяется только `firstBreedFreeClaimed`; успешное скрещивание атомарно (в том же обновлении состояния, что создаёт `HybridSeed`) устанавливает флаг в `true`; отменённая/отклонённая попытка флаг не меняет. Детали — §12, Slice 6.
2. **Повторная миграция отдельных specimens была недостаточно специфицирована** — `SAVE_VERSION >= 4` ошибочно можно было прочитать как эквивалент «у всех specimens есть `genomeV2`», что ломается в сценарии save→V4→V2 выключен→новый legacy specimen→V2 включён обратно. Введены два явно раздельных идемпотентных механизма: (1) глобальная миграция ресурсов/`labLevel`/обучающих флагов/pity — только один раз, при `SAVE_VERSION<4`; (2) `ensureGenomeV2Sidecars` — на каждой загрузке, безусловно, backfill `genomeV2` только тем specimens, у которых его нет, без перевыдачи ресурсов и без перезаписи существующих sidecars. Добавлены пять обязательных тестов (полный V3→V4, V4 с одним specimen без sidecar, V4 со смешанным массивом, V2→Legacy breed→V2, повторный backfill не меняет существующие sidecars). Детали — §7, §7.1, §7.2, §10.4, §12 Slice 1.
3. **Genetics V2 переходит на 9 визуальных локусов, не 8.** Существующий legacy-геном хранит независимый `leaf`-цвет (`leafPool`, 3 значения, аудит §3.2) отдельно от геометрии листа — при сведении в 8-локусную модель (где `leafForm`/форма листа и цвет листа делили один локус, либо цвет листа не имел собственного локуса вовсе) этот независимый признак либо терялся при миграции, либо переставал наследоваться как отдельное измерение. Решение: `leafColor` — самостоятельный девятый локус, наследуется независимо от `leafForm`. Обновлены таблица §1, §4.1, §7 п.3, все упоминания «8 локусов»/«восемь визуальных локусов» в этом документе. Полный каталог девяти локусов, включая точную комбинаторику (645 120 фенотипов/вид, 5 160 960 для восьми видов), формализован в новом документе `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` — созданном в этом же проходе.
4. **Статистическая терминология теста Mendelian inheritance смешивала генотип и фенотип.** Ожидание «фенотипы потомства 25/50/25» было неточным: 25/50/25 — это распределение **генотипов** (`AA`/`Aa`/`aa`) при скрещивании двух гетерозигот, а распределение **фенотипов** при **полном доминировании** (единственная модель Gate 1, кодоминирования нет) — классическое менделевское **75/25** (3:1). Тест 1 (§10.3) переписан на две раздельные проверки. Детали — §10.3.

Новых открытых продуктовых вопросов, блокирующих начало реализации Gate 1, по итогам этого прохода нет — это исправление формулировок и заполнение технического пробела, не новая развилка. **Gate 0 по-прежнему не принят владельцем** — этот проход не является актом принятия, реализация Slice 1 не начинается.

### 0.5. Проход 6 — Gate 0 принят; коррекция миграции `mutationId` перед стартом Slice 1

**Gate 0 принят владельцем 28.08.2026.** Перед стартом реализации владелец поймал ещё один дефект — на этот раз не в этом документе, а в `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.4 (таблица legacy→V2 миграции).

**Дефект**: §4.4 implementation contract требовал, чтобы `genomeV2.mutationId` мигрировавшего specimen всегда становился `null`, даже если у specimen был исторический legacy `mutationId` (`golden_vein`/`stardust`/`prism`/`phoenix`). Это нарушало собственное требование визуальной идентичности миграции (§7 п.4 этого документа: «внешний вид старого растения после миграции должен оставаться максимально идентичным») — применительно не к девяти локусам, а к мутациям: будущий V2-рендер, читающий только `genomeV2`, терял бы mutation-эффект и mutation rarity floor уже мутировавшего растения.

**Исправление** (только `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.4, эта таблица §4.4 не менялась — правило `mutationId` не входит в число девяти диплоидных локусов, миграция которых зафиксирована здесь, §7 п.3):

- Один из четырёх Gate-1-каталожных legacy `mutationId` (`golden_vein`, `stardust`, `prism`, `phoenix`) копируется **1:1** в `genomeV2.mutationId`.
- `null` мигрирует в `null`.
- Неизвестный/повреждённый ID (значение вне текущего каталога из четырёх legacy ID) не роняет загрузку save: `specimen.genome.mutationId` сохраняется без изменений (legacy-поле никогда не переписывается, §7 п.9 выше), а `genomeV2.mutationId` для этого одного specimen — `null` (безопасный дефолт для нераспознанного значения).
- Копирование — это перенос уже состоявшегося исторического результата, а не выдача новой мутации: миграция **не переигрывает** mutation roll и **не изменяет** `pityCounter` ни в одном из этих случаев — прямое следствие уже действующего правила §7.2 («`ensureGenomeV2Sidecars` не читает и не пишет pity»), которое теперь явно распространено и на `mutationId`.
- Новый обязательный тест: миграция покрывает все четыре legacy `mutationId` и `null` — см. §10.4.

Новых открытых продуктовых вопросов нет — это точечное исправление одной строки таблицы миграции, устраняющее прямое противоречие с уже принятым требованием визуальной идентичности, не новая развилка.

### 0.7. Проход 8 — pre-Slice-5 contract-lock pass (решения владельца перед стартом Slice 5)

Владелец принял Slice 3 (`ee3024f`) и Slice 4 (`e483c94`) по игровым результатам аудита прохода 7. Перед стартом Slice 5 (Nursery Tray, рост, постоянные растения) был проведён отдельный read-only аудит открытых технических вопросов уровня реализации (persisted-структуры, отличие legacy-семени от гибрида на грядке, момент создания `Specimen`, экономика Slice 5 vs Slice 6/7, минимальный UI, миграция/`SAVE_VERSION`) — полная таблица вопросов с цитатами существующих решений и явными CONTRACT GAP передана владельцу отдельно, не дублируется здесь построчно. Ниже — решения владельца по каждому найденному пробелу, зафиксированные до начала кода Slice 5.

1. **Хранение гибрида на грядке.** Не заводится отдельный `GameState.plantedHybrids`. `Plot` (`apps/web/src/game/types.ts`) расширяется одним аддитивным nullable-полем `hybridV2` с дискриминированным состоянием: `{ phase:'growing', hybrid: HybridSeedV2 }` (полный посаженный `HybridSeedV2`, включая геном — игроку он не показывается до созревания, см. §11 п.11) или `{ phase:'mature', specimenId, lastHarvestAt }` (постоянное растение, ссылка на единственный источник истины — `state.specimens`). Legacy-поля `Plot.seedId`/`Plot.plantedAt` не переименовываются и не удаляются. **Инвариант**: `hybridV2` и legacy-посадка (`seedId!==null`) никогда не сосуществуют на одной грядке — обеспечивается на уровне `GameStore.plantSeed()`/`GameStore.plantHybridSeedV2()` (обе проверяют, что грядка свободна от другого типа посадки, прежде чем сажать).
2. **Посадка.** Успех: `HybridSeedV2` атомарно удаляется из `nurseryTray`, тот же объект (без пересборки генома) переносится в `Plot.hybridV2` с установленными `plantedAt`/`plotId`, освобождая слот трея. Неуспех — полный no-op, семя остаётся в трее. Discriminated-результат с причинами: `seed_not_found`, `plot_not_found`, `plot_locked`, `plot_occupied` (грядка уже занята legacy-семенем или другим `hybridV2`).
3. **Рост.** Первый рост и повторный цикл определяются исключительно `genomeV2.speciesId` по таблице §2.1 этого документа (Солнечник 5/20 мин, Колокольник 8/30 мин) — вынесены в отдельную V2-конфигурацию (`apps/web/src/game/nurseryV2.ts`), **не** через legacy `SEED_BALANCE.growMs`. Ускорители роста (`entitlements`/`GARDEN_CONFIG`-бусты) на V2-рост в Slice 5 **не распространяются** — решение не принималось, оставлено как реальное elapsed-time без модификаторов; если это неверно, требует отдельного решения владельца в будущем slice.
4. **Создание `Specimen`.** Ровно один раз, в момент первого успешного сбора созревшего `HybridSeedV2`: `Specimen` добавляется в `state.specimens`, `Plot.hybridV2` атомарно переключается из `growing` в `mature` (тем же обновлением состояния), получая `specimenId`+`lastHarvestAt`. Присутствие `mature`-состояния с уже установленным `specimenId` — единственный и достаточный идемпотентный guard: повторный вызов сбора (или reload) не может повторно создать `Specimen`, потому что грядка уже не в состоянии `growing`.
5. **Коллекция.** Добавление в `state.specimens` происходит автоматически при первом сборе — отдельной кнопки/операции «перенести в коллекцию» нет (снимает противоречие формулировок §6 п.7/§10.5 из прохода 7 — обе точки зрения читаются как одно и то же событие). Растение одновременно существует в `state.specimens` (источник истины генома/фенотипа/родословной) и на грядке через `Plot.hybridV2.specimenId`.
6. **Legacy-совместимость нового V2 `Specimen`.** `Specimen.genome` (legacy, обязательное поле) заполняется детерминированной чистой функцией `projectGenomeV2ToLegacy(genomeV2): Genome` (`apps/web/src/game/legacyProjectionV2.ts`) — точное правило: `speciesId`→`shape`; выраженные `primaryColor`/`secondaryColor`/`leafColor` → обратные точные HEX-маппинги (инверсия таблиц `PRIMARY_HEX_TO_ID`/`SECONDARY_HEX_TO_ID`/`LEAF_COLOR_HEX_TO_ID` из `geneticsV2.ts`, той же самой таблицы, что использует прямая Slice 1 миграция — не заведена заново); выраженный `size`/`aura` → legacy-тир по имени (`size_giant`→`giant`, `aura_radiant`→`radiant` и т.д.); `pattern_solid`→`solid`, любой другой V2-pattern (`pattern_duotone`/`pattern_spots`/`pattern_stripes`/`pattern_veins`) →`duotone`; при результирующем legacy `solid` legacy `secondary` принудительно равен legacy `primary` (тот же инвариант, что уже действует в `genetics.ts` `randomGenome()`/`breed()`); `mutationId` копируется строкой как есть, включая `double_bloom`/`luminous_edge` (эти два ID не встречаются в legacy-сохранениях, но легитимны как строковое значение поля `Specimen.genome.mutationId`, которое типизировано как `string | null`, без ограничения известным legacy-каталогом); `stemForm`/`leafForm`/`flowerForm` не имеют legacy-полей и физически не могут попасть в результат (тип `Genome` их не содержит). Скрытые аллели **не уничтожаются** — они остаются как есть в `Specimen.genomeV2`, `projectGenomeV2ToLegacy` — чистая функция над уже выраженным фенотипом, ничего не пишет обратно в `genomeV2` и не вызывается повторно для уже существующего специмена (переключение флага V2→Legacy→V2 не меняет `genomeV2` ни на бит — legacy-режим лишь ЧИТАЕТ `genome`, никогда не пересчитывает его).
7. **Родословная.** `HybridSeedV2.parentIds` заполняется в момент успешного `breedNurseryV2()` в порядке `[seedParentId, pollenParentId]` (уже существующее поле типа с Slice 1, ранее не заполнялось). При созревании копируется в `Specimen.parentIds` без изменений. Отображение и работа с родословной — по-прежнему Slice 10; Slice 5 только не теряет уже доступные данные.
8. **Nursery Tray и скрещивание.** Новая store-level операция `breedNurseryV2(seedParentId, pollenParentId)` проверяет, в этом порядке, **до** вызова `breedV2` (Slice 3-4, без изменений): `seedParentId !== pollenParentId` → оба специмена существуют → у обоих есть `genomeV2` → `nurseryTray.length < 8`. При 8/8 (или любой из более ранних проверок) — `breedV2` не вызывается вообще: 0 RNG-вызовов, `pityCounter`/родители/tray/остальной `GameState` не меняются. После успешного `breedV2` — создаётся `HybridSeedV2` (не `Specimen`), добавляется в `nurseryTray`, сохраняется `nextPityCounter`. Species-валидация и её причины (`unsupported_species`/`interspecies_locked`) — без изменений, как приняты в Slice 3-4; они лишь дополняют перечень причин отказа `breedNurseryV2`, не заменяют его.
9. **Экономика.** В Slice 5 V2-скрещивание и V2-сбор (первый и повторный) не списывают/не начисляют `coins`/`pollen`/`geneticDust`, не переключают ни один из трёх обучающих флагов (`firstBreedFreeClaimed`/`firstHybridRewardClaimed`/`firstRecycleTopUpClaimed`). Пыльца и бесплатное первое скрещивание — Slice 6. Переработка — Slice 7 (см. п.10 ниже). Если после фильтрации доступно меньше двух поддерживаемых specimens — точный текст «Нужно как минимум две особи поддерживаемых видов.» (заменяет прежний общий текст «Нужно как минимум две особи с диплоидным геномом.», который теперь избыточен: список уже отфильтрован по поддерживаемым видам).

### 0.13. Проход 14 — contract-lock Slice 12 (Reveal, естественное раскрытие, контекстный onboarding, Люми-подсказки, Ботаническая книга, демо-повтор)

Пакет Slice 10-11 реализован (4 коммита, см. §0.12/статус), приёмка владельцем — вне этого прохода. Этим же проходом зафиксирован technical contract для **Slice 12** — полный текст в новом `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.14 (13 подразделов: persisted-состояние и дефолты для старых save, конечный автомат контекстного онбординга, каталог и условия подсказок Люми, структура view-model Reveal, структурный алгоритм происхождения признака, правило естественного раскрытия у родителей, идемпотентность повторного открытия Reveal, детерминированные фикстуры/RNG первых двух обучающих скрещиваний, гарантии демо-повтора, границы изоляции по feature-флагам, точные русские строки, порядок операций стора). Решения, зафиксированные владельцем (онбординг-спека `docs/GENETICS_ONBOARDING_SPEC.md`) до начала кода:

1. **Reveal — не отдельный экран поверх плота, а немедленный экран сразу после успешного `breedV2`**, до возврата в `LabPanelV2` (генотип потомка уже полностью известен в момент скрещивания — `HybridSeedV2`, Specimen создаётся только при сборе урожая, Slice 5). Происхождение каждого из 9 признаков вычисляется **структурно** из `AllelePair{a,b}` результата `breedV2` (сконвенция `inheritanceV2.ts`: `a` — всегда Seed Parent, `b` — всегда Pollen Parent) и выражённого фенотипа (`resolvePhenotypeV2`), не угадыванием по совпадению фенотипа с одним из родителей задним числом. Мутировавший признак (`aura`, если `result.mutated`) — всегда `✦ Новый признак`, происхождение по `a`/`b` для него не считается. Одновидовые родители — подписи «От первого/второго растения»; разновидовые — `← [Название вида]` (переиспользуется `SPECIES_NAME_BY_ID` из `hybridCardViewModel.ts`). Экран «Почему получилось так?» показывает только реально выражённые в потомке признаки — скрытые аллели родителей, не выраженные в потомке, никогда не раскрываются этим экраном.
2. **Естественное раскрытие — побочный эффект того же атомарного обновления стора, что и создание `HybridSeedV2`**, не отдельная операция. Для каждого локуса: если аллель, выраженный в потомке, был скрыт (не раскрыт) у конкретного родителя, для этого родителя раскрывается **только этот локус**, с `source:'natural'`, без списания пыли, без изменения других локусов, без перезаписи уже существующего `source:'microscope'` (микроскоп — платное осознанное действие игрока, естественное раскрытие никогда не понижает его результат). Если аллель скрыт у обоих родителей и выражен в потомке — раскрывается у обоих.
3. **Первый контекстный экран онбординга** (точный текст §13.1 онбординг-спеки: «Выбери два растения. Новое растение получит часть признаков от каждого. Иногда появляется совершенно новый признак.», кнопка «Понятно, начать») показывается один раз, персистентно (`geneticsIntroSeen`), только в Overhaul+V2, до первого реального V2-скрещивания — не заменяет саму механику выбора родителей. Старый 4-слайдовый `Onboarding.tsx` **не показывается**, когда Genetics V2 активен (Classic/Overhaul+Legacy — без изменений).
4. **Первые два обучающих скрещивания идут через реальный `breedV2`**, не фабрикуются вручную — с подменой RNG на детерминированный `mulberry32(seed)` (сиды и фикстуры генома двух стартовых Солнечников — уже существующие и протестированные в `mutationV2.test.ts`, контракт §4.6) **только** когда оба текущих родителя помечены `tutorialStarter:true` и счётчик `geneticsTutorialBreedsCompleted < 2`; во всех остальных случаях (обычная игра, ветеранские save, третье и далее скрещивание тех же растений) используется обычный `this.rng` без изменений. Первое скрещивание — гарантированно Uncommon, без мутации, с видимым признаком от каждого родителя. Второе — гарантированно раскрывает скрытый `size_large` у потомка и естественно раскрывает локус `size` у обоих родителей-стартеров, без мутации; перед вторым скрещиванием показывается точный текст о скрытом признаке (§13.1), после — точный текст о естественном раскрытии (§13.1: «Этот признак был скрыт у родителя — а у потомка стал видимым!»).
5. **Минимальная система подсказок Люми** — максимум одна активная подсказка одновременно, одна короткая фраза, немодальна (не блокирует ввод, не использует `sheet-backdrop`), каждая событийная подсказка показывается не более одного раза (персистентный `lumiHintsShown: string[]`), проигнорированные/закрытые подсказки не показываются повторно. Точный каталог фраз и условий появления — §7.3 онбординг-спеки, без добавления новых механик (L3/L4, `GeneLock`, погода — не затрагиваются, это только текстовые подсказки поверх уже существующих событий/состояния).
6. **Ботаническая книга — раздел «Генетика», разрешение задокументированного противоречия между документами.** `GENETICS_ONBOARDING_SPEC.md` и предыдущая версия `GENETICS_TARGET_DELTA.md` §12 п.12 расходились в перечне: зафиксировано, что раздел содержит **пять рабочих подразделов** (Родители, Наследование, Скрытые признаки, Мутации и pity, Пыльца и генетическая пыль) плюс **шестой**, честно помеченный «Скоро» (Ночные и погодные условия — реальная будущая механика, не выдумка, см. `docs/FINAL_VISION.md`). Пункт **«Показать обучение генетике заново» — отдельное действие книги** (запускает демо-повтор, §4.14.10), не является седьмым подразделом и не подменяет собой раздел 6. Книга может использовать точные технические термины (локус/аллель/доминантность) и точные проценты pity (открывается добровольно) — но не должна показывать `GeneLock`, Lab L3/L4, стабилизацию мутации, уже реализованные эффекты погоды или любые другие будущие механики как существующие.
7. **Демо-повтор обучения** — тот же UI (`RevealPanelV2`, `GeneticsIntroPanelV2`), но с зафиксированными демо-данными; структурно не может вызвать `breedV2`, создать `HybridSeed`/`Specimen` или изменить состояние экономики/сада (проверяется тестом на побайтовое равенство сериализованного состояния до/после полного прохода демо-повтора, §4.14.10).
8. **Изоляция.** Ничего из Slice 12 не доступно и не видно при выключенном Genetics V2 — `ClassicApp.tsx`, `GardenScene`, legacy `LabPanel.tsx`/`PlantPicker.tsx`/`AlbumPanel.tsx`, Supabase/SQL, Paddle/NFT, `SAVE_VERSION` (остаётся 4) — не затрагиваются. Единственный расшаренный файл — `LaboratoryScene.ts` (hotspot «Архивная книга»): помечается `implemented: GENETICS_V2_ENABLED` вместо жёстко `false`, Classic/Overhaul+Legacy продолжают видеть честный toast «скоро» без изменения поведения — подтверждается grep'ом бандла (см. итоговый отчёт по проходу).

## 2. Почему Gate 1 = только Солнечник и Колокольник

Без изменений относительно прохода 1: `sprout` (`speciesId:1`) и `common` (`speciesId:2`) — первые два вида в `SEED_BALANCE`, с полностью готовым арт-паком (3 стадии × 4 слоя + `_ref`). Уточнено владельцем: **Gate 1 поддерживает полноценное размножение (диплоидные локусы, mutation roll, межвидовое скрещивание между собой) только для этих двух видов.** Все остальные виды (3-8) остаются в статусе legacy до отдельного гейта — см. §3.

**Уточнение владельца (проход 3, correction-pass) — порядок открытия внутри Gate 1 для нового игрока:** Колокольник (`common`, `speciesId:2`) не доступен новому игроку с самого начала, несмотря на то, что оба вида полностью входят в состав Gate 1. Стартовая прогрессия:

1. У игрока есть один взрослый Солнечник.
2. Второй Солнечник он выращивает в первые 5 минут.
3. Первое бесплатное скрещивание — между двумя Солнечниками (одновидовое, не межвидовое — исправление ошибки прохода 2, где онбординг-документ описывал первое скрещивание как Солнечник×Колокольник).
4. Оно обучает только простой идее наследования видимых признаков — без демонстрации межвидового механизма.
5. Колокольник и Lab L2 открываются только после того, как первый `HybridSeed` вырастет до зрелого растения.

Это ограничение относится только к **прогрессии нового игрока** (онбординг), не к составу Gate 1 как такового — оба вида полностью поддерживаются с самого начала на уровне механики. Save с историей скрещиваний, получающие `labLevel=3` при миграции (§7 п.7), не проходят эту прогрессию заново — Колокольник и межвидовое скрещивание доступны им сразу, так как порог `labLevel>=2` уже пройден. Полная раскадровка этой прогрессии — `docs/GENETICS_ONBOARDING_SPEC.md`, §1-6.

Вопрос UX-реализации, не продуктовое решение этого документа (вывод, §11): как именно представлен недоступный Колокольник в UI до открытия (скрыт из магазина полностью vs показан заблокированным с подсказкой) — не блокирует начало реализации, конкретная форма выбирается на этапе Slice 5/8 (§12) — исправлена опечатка в ссылке на раздел (было ошибочно «§13» в проходе 3, там находятся onboarding gaps, не implementation slices).

### 2.1. Точное стартовое состояние Gate 1 (зафиксировано в проходе 4)

Устраняет расхождение деталей между delta, onboarding-спекой, GDD и xlsx (§0.2 п.18) — единое стартовое состояние нового/нетронутого save:

## 3. Legacy species (species 3-8) — политика доступа

Зафиксированное решение владельца, дословно:

1. Старые specimens species 3-8 **не удаляются** ни при миграции, ни при включении Genetics V2.
2. В Genetics V2 с ними можно: **просматривать** (карточка/альбом), **добавлять в избранное**, **перерабатывать** (по тарифу тира редкости, §5).
3. **Использовать как родителей Genetics V2 — нельзя**, пока для этих видов не реализованы соответствующие диплоидные локусы (стебель/лист/цветок-геометрия/узор — те, которых сейчас не существует вовсе, аудит §3.2). Кнопка/слот выбора родителя в UI лаборатории V2 должна либо не показывать specimens этих видов в списке доступных для скрещивания, либо показывать их визуально отключёнными с понятной причиной (конкретная форма — вопрос UX-реализации, не продуктовое решение этого документа).
4. При выключенном Genetics V2 (`VITE_DIPLOID_GENETICS_ENABLED=false`) — весь legacy-режим (включая скрещивание specimens любого вида, 1-8) продолжает работать буквально как описано в `docs/GENETICS_CURRENT_STATE_AUDIT.md`, без каких-либо изменений поведения.

Следствие для миграции сохранений (§7): specimen с `genome.shape` в диапазоне 3-8 в старом сохранении мигрирует в диплоидную структуру той же гомозиготной политикой, что и specimens species 1-2 (§7, пункт 1-4) — новых правил специально для legacy-видов миграция не вводит, ограничение «нельзя как родителя V2» применяется на уровне UI/логики скрещивания, не на уровне формата сохранённых данных.

## 4. Genetics V2 — механика наследования и mutation roll

Зафиксированные решения владельца, сведены в одну расчётную модель:

### 4.1. Обычное наследование (без мутации)

Каждый из **девяти** локусов (исправлено в проходе 5, §0.4 п.3 — было восемь; полный каталог `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4) — пара аллелей у каждого родителя. Потомок получает **по одному аллелю от каждого родителя на каждый локус** (аллель выбирается 50/50 из пары этого родителя — прямое расширение уже существующего принципа `inherit(a,b,rng) = rng()<0.5 ? a : b` (`genetics.ts:65-67`), применённое к аллелю, а не к целому гену). **Никакого шанса подмены на случайное значение пула на этом шаге нет** — старый независимый `GENE_MUTATE_CHANCE=0.08` не переносится в V2 ни в каком виде. Видимый фенотип локуса — по таблице доминирования (`DOMINANCE_TABLE`, состав — вопрос дизайна локусов, не этого документа).

Species-локус (`speciesId`+body rig) — исключение из общего правила: не участвует в парном 50/50-наследовании аллелей, копируется от Seed Parent целиком, всегда.

### 4.2. Mutation roll

Один ролл на скрещивание, определяющий, произойдёт ли мутационное событие в этом скрещивании:

| Попытка после последней мутации | Шанс |
|---:|---:|
| 1 | 3% |
| 2 | 4% |
| 3 | 5% |
| 4 | 6% |
| 5 | 7% |
| 6 | 8% |
| 7 | 9% |
| 8 | 10% |
| 9 | 11% |
| 10 | 100% (гарантия) |

Ожидание — то же значение, что и в листе `Pity` балансировочной таблицы xlsx: около **7.85** скрещивания на мутационное событие (используется как контрольное число статистического теста, §10, тест 2).

- **Pity сбрасывается только после успешного mutation event** — не после обычного 50/50-наследования, потому что обычное наследование в V2 больше не содержит никакого случайного «срыва» само по себе (в отличие от текущей плоской модели, где сброс происходит при любой per-gene мутации, аудит §4.3 — эта развилка теперь закрыта однозначно).
- Мутационное событие **никогда не меняет `speciesId`** потомка — жёсткое ограничение, отдельное от общего механизма роллов (species-локус физически не входит в пространство значений, которые mutation roll может затронуть).

### 4.3. Что производит успешный mutation roll (вывод из решений, см. §11 п.1)

Зафиксированные решения дают классификацию 6 конкретных `mutationId` по тирам (§9), но не переопределяют явно веса выбора тира внутри успешного ролла — унаследовано из GDD v3 (документ-источник, раздел «Тиры мутационного события»): Minor 70% / Major 25% / Signature 5%. Для Gate 1, при успешном mutation roll: сначала выбирается тир по этим весам, затем — конкретный `mutationId` из каталога §9, ограниченного этим тиром (Minor: `golden_vein`/`double_bloom`; Major: `stardust`/`prism`/`luminous_edge`; Signature: `phoenix`). Итоговая редкость потомка форсируется не ниже `minRarity` выбранной мутации — тот же принцип, что уже работает в текущей `rarityOf()` (аудит §4.5), не новый механизм.

## 5. Пыльца и генетическая пыль

### 5.1. Пыльца

| Операция | Цена |
|---|---:|
| Одновидовое скрещивание | 8 пыльцы |
| Межвидовое скрещивание | 12 пыльцы |
| Первое обучающее скрещивание | бесплатно |

Производится зрелыми растениями (начисляется при сборе, аналогично тому, как сейчас `harvest()` начисляет монеты, `store.ts:258` — новая параллельная начисление, не замена монетной награды за урожай). «Первое обучающее скрещивание бесплатно» — реализуется через персистентный флаг `firstBreedFreeClaimed` в `GameState` (§6.2, проход 4), не только через аналитический `isFirstBreedAttempt()`/`markBreedAttempted()` (`LabPanel.tsx:10-24`), который остаётся исключительно для аналитики.

**Формула пыльцы за сбор (зафиксировано в проходе 4, синхронизировано с `genesis-garden-balance-model-v3.xlsx`, лист `Rarity`, колонка «Пыльца +»):**

```
пыльца_за_сбор = speciesBasePollen + rarityBonus
```

| Редкость | rarityBonus |
|---|---:|
| Common | +0 |
| Uncommon | +0 |
| Rare | +1 |
| Epic | +1 |
| Legendary | +2 |
| Mythic | +2 |

`speciesBasePollen` — по таблице §2.1 (2 для Солнечника и Колокольника в Gate 1). Значения `rarityBonus` уже присутствовали в xlsx до этого прохода и совпадают с зафиксированным решением без расхождений.

### 5.2. Генетическая пыль

**Реализовано в Slice 7 (проход 10)** — переработка (единственный источник пыли в Genetics V2, таблицы ниже) была спроектирована уже в проходе 8 (перенесена из Slice 5), но код появляется только этим проходом. До Slice 7 (Slice 5-6) UI заполненного питомника предлагал игроку только посадить одно из семян (§6) — без предложения переработать; начиная со Slice 7 к этому тексту добавляется действие «Переработать» на каждом семени трея (§6.1 UI-контракт, contract §4.10.5).

**Скрещивание в Genetics V2 не выдаёт пыль** — единственный источник пыли теперь переработка, по одной и той же редкости (`rarityOfV2(genomeV2, genomeV2.mutationId)` — не напрямую по `mutationId`) в двух ставках, полной и половинной:

| Тир | Пыль за переработку выращенного `Specimen` (100%) | Пыль за переработку `HybridSeed` в Nursery Tray (`max(1, floor(full/2))`) |
|---|---:|---:|
| Common | 1 | 1 |
| Uncommon | 2 | 1 |
| Rare | 5 | 2 |
| Epic | 12 | 6 |
| Legendary | 30 | 15 |
| Mythic | 80 | 40 |

Правый столбец зафиксирован именно через `Math.floor`, не округление до ближайшего — снимает неоднозначность 50% для Rare: `floor(5/2)=2`, не 3 (округление вверх дало бы неверные 3). `max(1, …)` гарантирует, что переработка семени никогда не даёт 0 пыли даже для Common (`floor(1/2)=0` → поднимается до 1).

### 5.3. Обучающий грант пыльцы и пыли (одноразово, зафиксировано в проходе 3, first-recycle top-up реализован в Slice 7)

Два отдельных одноразовых обучающих гранта, наложенных поверх обычной экономики §5.1/§5.2 — не постоянные источники, срабатывают ровно один раз за сохранение:

1. **8 пыльцы при первом открытии.** Как только первый `HybridSeed` вырастает до зрелого `Specimen` — засчитывается обучающая цель «Первое открытие», игрок получает **8 пыльцы** (ровно стоимость следующего одновидового скрещивания, §5.1) одновременно с открытием Колокольника и Lab L2 (§2, §6.1). Это грант поверх обычного начисления пыльцы при сборе — не замена его. **Реализовано в Slice 8 (проход 11)**: гейтится единственным условием `!firstHybridRewardClaimed`, проверенным одинаково и при первом созревании гибрида, и при повторном сборе уже зрелого — так существующие save (Slice 5-7) с уже зрелым, но ещё не засчитанным гибридом получают грант на ближайшем сборе без необходимости выращивать «ещё одного первого» (contract §4.11.1).
2. **Компенсация пыли до 3 при первой переработке (реализовано в Slice 7).** `firstRecycleTopUpClaimed` относится к **первой успешно завершённой настоящей переработке независимо от типа цели** — неважно, был это `HybridSeed` из трея или выращенный `Specimen`: то, что случится первым в реальной игре одного save. Правило: посчитать обычную награду по тарифу тира (§5.2, соответствующий столбец — полный или половинный); если флаг `firstRecycleTopUpClaimed === false` и посчитанная награда меньше 3 — добавить разницу до ровно 3 (столько стоит операция микроскопа, §6.1); если награда уже 3 или больше — бонус не добавляется (условие, не гарантированная константа сверху тарифа); после ЛЮБОЙ успешно завершённой первой переработки (семя или specimen) флаг атомарно становится `true` — той же атомарной операцией, что удаляет цель и начисляет пыль; неудачная, отменённая или отклонённая операция (favorite, not found, ambiguous plot, отмена UI-подтверждения) флаг не меняет. Успешный результат store-метода несёт `baseDust`/`topUpDust`/`dustGained` (итоговая сумма) отдельными полями — UI показывает игроку только `dustGained`, без разделения на тариф и компенсацию (contract §4.10.2). Это одноразовая tutorial-компенсация конкретно для первой переработки, не постоянный источник пыли и не изменение тарифа §5.2 как такового.

Оба гранта — часть обучающего контура, детали UX/триггеров — `docs/GENETICS_ONBOARDING_SPEC.md`, §6.

## 6. Nursery Tray и выращивание

Обязателен для Gate 1, полный контракт:

1. Вместимость — **8 семян**.
2. Скрещивание создаёт `HybridSeed` (геном уже определён и зафиксирован в момент скрещивания — детерминированно посчитан по §4, но **не показывается игроку** как готовый specimen), помещаемый в Nursery Tray — не готовый `Specimen` сразу, в отличие от текущей плоской модели (аудит §1, шаг 5-6, §7).
3. При заполненном Tray (8/8) — **новое скрещивание блокируется** до освобождения места (посадка одного из семян — переработка семени из трея сдвинута в Slice 7, см. §5.2, п.10 ниже). UI обязан заранее, до попытки скрестить, показывать состояние «Питомник заполнен: 8/8» — не просто отклонять клик по кнопке «Скрестить» без объяснения.
4. `HybridSeed` нужно **посадить** на грядку — использует ту же по духу логику роста по временнóй дельте, что уже работает для магазинных семян (`plotStatus`, `store.ts:178-192`), но для нового типа данных, не `SeedDef`, и по отдельной V2-конфигурации тайминга (§2.1, §10 п.3 ниже), не по `SEED_BALANCE.growMs`.
5. После созревания `HybridSeed` становится полноценным `Specimen` — только в этот момент игроку становится виден полный фенотип (в отличие от текущей модели, где геном известен мгновенно в момент клика «Скрестить», аудит §7).
6. Зрелое растение **остаётся на грядке** после сбора продукта (§1 таблицы, «Постоянные зрелые растения») — не исчезает, как сейчас происходит с магазинными семенами при `harvest()` (аудит §8). В Slice 5 сбор — чистая механика (растение проявляется/обновляется таймер повторного цикла), без пыльцы (Slice 6) и без переработки (Slice 7, п.10 ниже).
7. Добавление в коллекцию (`state.specimens`) происходит **автоматически** в момент первого сбора — отдельного действия «перенести в хранилище» нет (проход 8, §0.7 п.5, устраняет прежнюю двусмысленность формулировки). Растение при этом одновременно существует в `state.specimens` (источник истины) и на грядке через ссылку. Дальше specimen можно: использовать как родителя следующего скрещивания (Slice 5+), переработать (Slice 7).
8. Посадка и выращивание гибрида — **обязательная часть** E2E-сценария Gate 1 (§10).
9. **Технический контракт хранения (проход 8, §0.7).** Персистентная структура — не отдельный массив посаженных гибридов, а одно аддитивное nullable-поле `Plot.hybridV2` с дискриминированным состоянием `growing`/`mature`; discriminated-результат для посадки (`seed_not_found`/`plot_not_found`/`plot_locked`/`plot_occupied`); идемпотентный guard создания `Specimen` — присутствие `mature`-состояния с уже установленным `specimenId`. Полный тип и правила — `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.8.
10. **Legacy-совместимость (проход 8, §0.7 п.6).** Каждый рождённый V2-`Specimen` получает обязательный legacy `genome` через чистую функцию `projectGenomeV2ToLegacy()` — точное правило маппинга (цвета, размер, аура, узор, `mutationId`) — §4.8 контракта. Скрытые аллели не уничтожаются, `genomeV2` не пересчитывается при переключении флага.

## 6.1. Видимость скрытой генетики: простая/расширенная карточка, микроскоп, Why-экран, `GeneLock`

Зафиксировано в проходе 3 (микроскоп), **расширено и исправлено в проходе 4** (единый контракт видимости) — устраняет два противоречия: прохода 2 (`docs/GENETICS_ONBOARDING_SPEC.md` уже обучал игрока микроскопу, а этот документ одновременно исключал микроскоп из Gate 1 целиком) и прохода 3 (расширенная карточка бесплатно показывала оба аллеля и полный список скрытых признаков — обесценивая платное раскрытие микроскопом, §0.2 п.15).

### Единый контракт видимости скрытой генетики (зафиксировано в проходе 4)

- **Простая карточка** (§8 onboarding-спеки) показывает **только выраженный фенотип** — ни одного скрытого признака, ни в каком виде.
- **Расширенная карточка без исследования** показывает по каждому локусу **выраженный аллель** (тот, что виден у растения), второй аллель — как **«Не исследован»**, без значения и без указания доминирования.
- **Точное значение второго аллеля и его доминирование** показываются только **после раскрытия**: либо микроскопом (ниже), либо **естественным раскрытием** — если этот же скрытый аллель родителя фактически проявился у потомка, и Reveal однозначно показал его происхождение (§4.2, второе обучающее скрещивание — прямой пример), этот конкретный признак **у этого родителя** считается раскрытым естественным путём. Остальные скрытые признаки этого родителя (и любые скрытые признаки, не проявившиеся у данного потомка) остаются нераскрытыми.
- **Экран «Почему получилось так?»** (§11 onboarding-спеки) **не раскрывает бесплатно всю генетику родителей** — показывает происхождение только тех признаков, которые **фактически проявились** у потомка (то же ограничение, что и у Reveal, §3.3 onboarding-спеки, только подробнее по каждому проявившемуся признаку).

Раскрытие (микроскопом или естественным путём) персистентно на уровне **конкретного экземпляра** (`Specimen`), не вида и не генотипа — раскрытие одного растения не влияет на то, что видно у других specimens того же генотипа, включая его собственных потомков.

### Минимальный микроскоп — входит в Gate 1

**Реализовано в Slice 8 (проход 11)** — `apps/web/src/game/microscopeV2.ts` + `GameStore.revealHiddenLocusV2()`, точный порядок проверок и тексты — contract §4.11.3/§4.11.4.

Открывается вместе с Lab L2 (`labLevel>=2` — в Gate 1 этот же порог снимает только гейт Колокольника, **не** межвидовое скрещивание: interspecies остаётся заблокировано до Slice 9, см. правку ниже и contract §4.11.2). Единственная операция, доступная в Gate 1:

1. Выбрать растение (specimen) из коллекции/грядки.
2. Выбрать **один скрытый признак этого растения — категорией, понятной игроку**: «Цвет», «Форма цветка», «Узор» и т.п. (не «локус» — слово не используется в UI микроскопа, тот же принцип простого языка, что и везде до расширенной карточки/Книги, `GENETICS_ONBOARDING_SPEC.md` §0).
3. Потратить **3 генетической пыли**.
4. Скрытый аллель этого признака раскрывается **навсегда** — персистентно для этого конкретного экземпляра (не глобально, не для вида и не для будущих потомков этого растения).

**Ограничения выбора (зафиксировано в проходе 4):**

- Выбирать можно **только** признак с **реально нераскрытым** скрытым аллелем — уже раскрытые (микроскопом или естественным путём, см. выше) и кодоминантные признаки (у которых по определению нет единственного «скрытого» состояния — оба аллеля выражены одновременно) в списке выбора **не предлагаются**.
- Повторно оплатить уже раскрытый или кодоминантный признак **нельзя** — ни по ошибке, ни намеренно (список показывает только реально доступные варианты, кнопка недоступна для остальных).
- Если у растения **нет** ни одного доступного для раскрытия признака (все раскрыты естественно/микроскопом, либо все кодоминантны) — экран показывает: «У этого растения нет нераскрытых скрытых признаков». **Пыль в этом случае не списывается.**

Технический вывод (не продиктован дословно, вывод из решения — см. §11): раскрытие хранится как поле на уровне `Specimen` (например, множество раскрытых признаков/локусов, с пометкой источника — микроскоп vs естественное раскрытие, для консистентности UI между простой/расширенной карточкой и Why-экраном), не на уровне `Genome`/вида.

### Явно не входит в Gate 1

- `GeneLock` (закрепление аллеля за пыль перед скрещиванием) — см. ниже.
- Стабилизация мутации.
- Полный прогноз всех вероятностей по исследованным родителям.
- Сложные исследования.
- Любая другая функциональность Lab L3/L4.

### `GeneLock` — статус

Полностью исключён из Gate 1:

- Возвращён на **Lab L3** (вне Gate 1 — Gate 1 покрывает только L1 и L2).
- Целевая цена на будущее, когда механика будет реализована за пределами Gate 1: **10 генетической пыли** (не текущие 8 из legacy-реализации, аудит §1 шаг 3 — новая цена относится только к будущей V2-версии, не переносится автоматически из текущего кода).
- В интерфейсе Gate 1 (лаборатория L1/L2) `GeneLock` **не отображается вообще** — ни активной кнопкой, ни disabled-состоянием, ни заглушкой «скоро» (в отличие, например, от хотспотов «Архивная книга»/«Сушильный шкаф», которые в проходе 1 аудита честно помечены «скоро» — `GeneLock` в Gate 1 не должен быть виден игроку ни в каком виде).
- При выключенном Genetics V2 (`VITE_DIPLOID_GENETICS_ENABLED=false`) legacy UI сохраняет существующий `GeneLock` без каких-либо изменений — прямое следствие уже действующей политики флагов (§8 п.3): Classic/legacy-режим не знает о новом флаге вообще.

Implementation slice для этого раздела — Slice 8 (§12): «Lab L2 и минимальный микроскоп», после переработки (Slice 7) и до межвидового скрещивания (Slice 9).

## 6.2. Экономическое состояние обучения хранится в save

Зафиксировано в проходе 4 (§0.2 п.16) — заменяет использование аналитического `localStorage`-флага как источника истины для игровой экономики.

**Проблема:** существующий `localStorage['genesis-garden-first-breed-v1']` (аудит, `isFirstBreedAttempt()`/`markBreedAttempted()`, `LabPanel.tsx:10-24`) — это ключ в `localStorage`, отдельный от `GameState`/save. Он не переживает смену устройства/браузера предсказуемо, не входит в save-миграцию, не тестируется как часть `store.test.ts`, и в принципе не должен решать, бесплатна ли операция — это была всего лишь аналитика.

**Решение:** три персистентных булевых поля в `GameState`:

- `firstBreedFreeClaimed` — бесплатное первое скрещивание уже использовано.
- `firstHybridRewardClaimed` — обучающий грант 8 пыльцы + открытие Колокольника/Lab L2 (§2.1, §5.3 п.1) уже выдан.
- `firstRecycleTopUpClaimed` — компенсация пыли до 3 при первой переработке (§5.3 п.2) уже выдана.

**Правила:**

1. Флаг меняется **только** после успешно завершённой операции — не в момент попытки.
2. Неудачная/отменённая попытка скрещивания (например, игрок закрыл экран подтверждения) **не расходует** бесплатную попытку — `firstBreedFreeClaimed` остаётся `false` до фактического завершённого `breedV2`.
3. Повторное обучение из настроек (`GENETICS_ONBOARDING_SPEC.md` §14) **не изменяет** ни одно из трёх полей.
4. Переключение feature flags (§8) **не сбрасывает** эти поля — они часть `GameState`, не зависят от того, какой генетический движок активен в данный момент.
5. Save с историей скрещиваний (§7, критерий «история скрещиваний») получает **все три поля `true`** при миграции — ветеран не должен видеть обучающие гранты как всё ещё доступные.
6. Новый или нетронутый save получает **все три поля `false`**.
7. Это часть миграционной таблицы (§7) и обязательных тестов Slice 1 (§10.4, §12).

`isFirstBreedAttempt()`/`markBreedAttempted()` (`localStorage`) **сохраняется без изменений**, но переквалифицируется на чисто аналитическую роль — не используется для решения «бесплатна ли операция» нигде в Genetics V2 коде.

## 6.3. Миграция pity

Зафиксировано в проходе 4 (§0.2 п.17).

**Формула миграции существующего `pityCounter`:**

```
v2PityCounter = clamp(floor(existingPityCounter), 0, 9)
```

Смысл: значение `9` означает, что следующая V2-попытка использует гарантированные 100% (10-я строка таблицы pity, §4.2). Миграция **не сбрасывает** накопленный игроком прогресс к мутации — прямое продолжение уже действующего принципа «миграция не должна ощущаться как потеря прогресса» (§7 в целом).

**Первое и второе настоящие обучающие скрещивания** (§3, §4 `GENETICS_ONBOARDING_SPEC.md`):

- проходят через **реальный** `breedV2` — не отдельную ветку кода с подменённым результатом (тот же принцип, что уже зафиксирован для гарантии результата, `GENETICS_ONBOARDING_SPEC.md` §3.2);
- **гарантированно не создают** mutation event (это же требование уже зафиксировано как часть гарантии читаемого результата);
- **поэтому считаются обычными неудачными mutation attempts** и увеличивают `pityCounter` на 1 каждое — так же, как любое другое одновидовое скрещивание без мутации;
- итог: после первых двух обучающих скрещиваний нового игрока `pityCounter = 2` (при условии, что оба — единственные скрещивания на этот момент).

**Повторный демонстрационный tutorial (повтор обучения из настроек, `GENETICS_ONBOARDING_SPEC.md` §14) `pityCounter` не меняет** — он не вызывает реальный `breedV2` вообще (тот же принцип, что уже зафиксирован для отсутствия повторной выдачи ресурсов, §6.2 выше).

Отдельные unit-тесты для этого раздела — §10.4.

## 7. Безопасная миграция старых сохранений

Полностью заменяет §3 предыдущей версии документа — все девять пунктов ниже являются прямыми решениями владельца, не предположениями аудита.

1. **Геном мигрирует через гомозиготность.** Для каждого существующего видимого признака старого плоского генома создаётся пара одинаковых аллелей: `locus.a = locus.b = currentValue`. Это единственная утверждённая политика (в проходе 1 фигурировала как вариант (A) среди двух рассматриваемых — теперь закреплена, вариант (B) отклонён).
2. **Случайные скрытые аллели старым растениям не генерируются.** Прямое следствие пункта 1 — раз оба аллеля равны видимому значению, скрытого состояния не возникает, и генерировать его дополнительно не нужно (и не следует).
3. **Для новых геометрических локусов (тех, которых в плоской модели не было вовсе — `stemForm`, `leafForm`, `flowerForm`, геометрический `pattern`) — нейтральные дефолтные аллели, заданные стабильными семантическими ID, не числовыми индексами.** Зафиксировано владельцем в проходе 3: `stem_standard`, `flower_standard`, `pattern_solid`, `leaf_standard`. **Уточнено в проходе 5 (§0.4 п.3), после перехода на 9-локусную модель**: `leaf_standard` — это дефолт для **формы** листа (`leafForm`), брand-new локуса, которого в плоской модели не было вовсе. Legacy-поле `leaf` (цвет) — это отдельная история: оно мигрирует не сюда, а в новый независимый локус `leafColor` по обычной гомозиготной фикции пункта 1 выше (`leafColor.a = leafColor.b = соответствующий leaf_color_* по legacy-цвету`), не как нейтральный дефолт. Полная lossless-таблица legacy→V2, локус за локусом — `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.4. Локус существует у мигрировавшего specimen с самого начала (не `undefined`), гомозиготен по этому ID (`locus.a = locus.b = "stem_standard"` и т.д.) — не случайное и не производное от чего-либо в старом геноме значение. Каждый ID должен ссылаться на визуальный вариант, **максимально повторяющий существующий legacy-ассет** — миграция не должна визуально менять старое растение (то же требование идентичности, что и в пункте 4 ниже, здесь — явно распространено и на новые локусы, не только на перенесённые). Сама привязка ID → конкретный визуальный вариант/арт-ассет — техническая задача реализации/art-pass, не отдельное продуктовое решение (вывод, §11) — но схема именования и семантика («что означает „стандартный"») зафиксированы владельцем окончательно, вопрос закрыт как продуктовый.
4. **Внешний вид старого растения после миграции должен оставаться максимально идентичным.** Это ограничение проверяется тестом (§10) — рендер мигрировавшего specimen до и после миграции должен визуально совпадать по всем полям, унаследованным из старого генома (пункты 1-2 это гарантируют структурно: гомозиготный локус всегда выражает то же видимое значение, что было).
5. **Родословная старых specimens — `unknown`/`null`, без попытки реконструкции.** Применяется единообразно ко всем мигрировавшим specimens, включая species 1-2 и legacy species 3-8 — старый `Specimen` не хранит ссылки на родителей вообще (аудит §2), восстанавливать нечего.
6. **Критерий «save имеет историю скрещиваний»** — хотя бы одно из:
   - `specimens.length > 2` (то есть больше двух стартовых);
   - `pityCounter > 0`;
   - `geneticDust > 0`.
7. **Save с историей скрещиваний получает:** `pollen = 24`, `labLevel = 3`, все три обучающих флага `true` (§6.2), `pityCounter` мигрирует по формуле §6.3.
8. **Нетронутый save (не подходит ни под одно условие пункта 6) получает:** `pollen = 0`, `labLevel = 1`, все три обучающих флага `false` (§6.2), `pityCounter = 0` (по формуле §6.3 — гарантированно 0, поскольку `pityCounter>0` само является одним из условий «истории», п.6) — трактуется как эквивалент нового игрока, даже если технически сохранение уже существовало на диске.
9. **Миграция детерминирована, идемпотентна, не изменяет данные повторно при переключении флага.** Прямое расширение уже действующего в коде принципа (аудит §10.2, `store.ts:63-64`: «миграции только добавляют недостающие поля»). **Исправлено в проходе 5 (§0.4 п.2) — устраняет дефект прохода 4**: `SAVE_VERSION >= 4` (или, эквивалентно, «глобальная миграция уже выполнялась для этого save») **нельзя** считать эквивалентом «у каждого specimen в этом save есть `genomeV2`». Это два раздельных механизма с разными условиями запуска — см. §7.2 ниже. `SAVE_VERSION` повышается с 3 до 4 один раз, при первом обнаружении `SAVE_VERSION < 4` (условие «есть ли этот save уже на V4», не «есть ли у этого specimen sidecar»).

### 7.2. Два раздельных механизма миграции (исправлено в проходе 5, §0.4 п.2)

**Проблема, обнаруженная владельцем**: если трактовать `SAVE_VERSION >= 4` как гарантию «все specimens уже имеют `genomeV2`», следующий сценарий ломает save необнаружимо:

1. Save мигрировал в V4 (глобальная миграция ресурсов прошла один раз, `SAVE_VERSION` стал 4).
2. Игрок выключил Genetics V2 (`VITE_DIPLOID_GENETICS_ENABLED=false`).
3. Игрок создал новое растение через legacy-генетику (legacy engine ничего не знает о `genomeV2` и не создаёт sidecar — прямое следствие политики феличных флагов, §8 п.3/п.7: legacy-код физически не читает и не пишет новые поля).
4. У нового specimen нет `genomeV2`, при этом `SAVE_VERSION` уже равен 4.
5. Игрок включил Genetics V2 обратно.

Если код на загрузке проверяет только `SAVE_VERSION < 4` для решения «нужно ли мигрировать геномы», этот конкретный specimen навсегда останется без `genomeV2` — код молча пропустит его как «уже мигрированный save», хотя фактически не все specimens мигрированы. Это заставило бы V2-код либо падать, либо втихую скрывать specimen из UI лаборатории без объяснения.

**Решение — два раздельных механизма, с разными условиями запуска, оба идемпотентны:**

1. **Глобальная миграция ресурсов (V3→V4, запускается ровно один раз).** Условие запуска: `SAVE_VERSION < 4`. Мигрирует **только** save-уровневые поля: `pollen`, `labLevel`, три обучающих флага (§6.2), `pityCounter` (по формуле §6.3), согласно критерию «история скрещиваний» (п.6-8 выше) и матрице §7.1. После выполнения `SAVE_VERSION` становится `4`; повторно на дальнейших загрузках **не запускается** (условие `SAVE_VERSION < 4` больше не истинно). Эта миграция **не создаёт и не трогает** `genomeV2` ни одного specimen — это отдельная забота следующего механизма.
2. **`ensureGenomeV2Sidecars` — идемпотентный backfill, запускается при каждой загрузке save.** Условие запуска: **безусловно, каждый раз**, когда save загружается (не гейтится `SAVE_VERSION`). Проходит по **всем** `state.specimens` и для каждого, у которого `specimen.genomeV2 === undefined`, детерминированно строит sidecar по правилам гомозиготной миграции пунктов 1-4 выше (`stem_standard`/`flower_standard`/`pattern_solid`/`leaf_standard` для новых геометрических локусов, гомозиготная фикция для перенесённых видимых признаков). Specimens, у которых `genomeV2` уже присутствует (мигрировавшие ранее ИЛИ рождённые напрямую в Genetics V2), **не трогаются вообще** — существующий sidecar никогда не перезаписывается и не пересчитывается повторно, ни частично, ни полностью.

**Свойства `ensureGenomeV2Sidecars` (обязательны, тестируются §10.4):**

- Выполняется на **каждой** загрузке save, независимо от `SAVE_VERSION` и от того, включён ли сейчас `VITE_DIPLOID_GENETICS_ENABLED` (backfill — это гигиена данных save, не UI-логика; он должен поддерживать sidecar-поле консистентным независимо от того, каким движком игрок сейчас пользуется, чтобы включение флага в любой момент сразу видело корректные данные).
- **Не** перевыдаёт `pollen`, `labLevel`, обучающие флаги или `pityCounter` — эти поля принадлежат исключительно глобальной миграции (механизм 1) и `ensureGenomeV2Sidecars` их не читает и не пишет ни при каких условиях. Backfill одного specimen — это исключительно операция над `Specimen.genomeV2`, не над `GameState` в целом.
- Идемпотентен по построению: `specimen.genomeV2 === undefined` — единственное условие, решающее, создавать ли sidecar для этого specimen; после первого прохода условие становится ложным для этого specimen, и повторный вызов backfill на нём — no-op.
- Корректно восстанавливает **смешанный** V4-save (часть specimens уже с `genomeV2`, часть без — сценарий выше) за один проход по массиву, без дополнительных флагов уровня save.
- Не требует `SAVE_VERSION >= 4` как предусловие — техническая гигиена не выключенная в предыдущей ревизии этого документа: если save ещё **не** прошёл глобальную миграцию (`SAVE_VERSION < 4`), backfill всё равно безопасно проходит по specimens **после** того, как механизм 1 отработал в рамках той же загрузки (порядок вызова: сначала глобальная миграция при необходимости, затем `ensureGenomeV2Sidecars` — всегда), так что после однократной загрузки любой save оказывается и на `SAVE_VERSION 4`, и с sidecar на каждом specimen одновременно.

## 8. Feature flags

1. Новый отдельный флаг `VITE_DIPLOID_GENETICS_ENABLED` (по аналогии с уже существующим `VITE_VISUAL_OVERHAUL_ENABLED`, `game/featureFlags.ts:8-9` — то же булево чтение `import.meta.env`).
2. Genetics V2 активируется **только** если одновременно: `VITE_VISUAL_OVERHAUL_ENABLED=true` **и** `VITE_DIPLOID_GENETICS_ENABLED=true`.
3. **Classic UI (`ClassicApp.tsx`) всегда использует legacy-генетику** — вне зависимости от значения `VITE_DIPLOID_GENETICS_ENABLED`. Это значит проверка флага диплоидной генетики физически не должна происходить нигде на пути `ClassicApp` — не «показываем, но выключено», а полностью тот же код, что и сегодня.
4. **Исправлена формулировка «2 продуктовых состояния» (проход 4, §0.2 п.20).** Она была неточной: фактически существуют **три достижимых режима UI**, но только **два генетических движка**:

   | № | `VISUAL_OVERHAUL_ENABLED` | `DIPLOID_GENETICS_ENABLED` | UI | Генетический движок |
   |---:|---|---|---|---|
   | 1 | `false` | любое значение | Classic UI | Legacy genetics |
   | 2 | `true` | `false` | Overhaul UI | Legacy genetics |
   | 3 | `true` | `true` | Overhaul UI | Genetics V2 |

   Режим 1 — не «два независимых флага дают 4 состояния»: при `VISUAL_OVERHAUL_ENABLED=false` значение `DIPLOID_GENETICS_ENABLED` не имеет никакого эффекта (Classic UI его не читает вообще, см. п.3) — это одно состояние, не два, несмотря на то, что булева комбинация формально различима. Итого **три достижимых режима**, не четыре и не два, но **только два генетических движка** (legacy и V2) — режимы 1 и 2 используют один и тот же движок под разными UI.
5. **Все три режима должны иметь regression coverage** (уточнено в проходе 4) — не только «Classic не ломается» и «Overhaul+V2 работает», но и отдельно режим 2 (Overhaul+Legacy, текущее поведение ветки `visual-overhaul` до этого прохода) — тот же принцип, что уже подтверждён для `VISUAL_OVERHAUL_ENABLED` на предыдущих этапах (аудит §10.2/`IMPLEMENTATION_STATUS.md`), теперь явно распространён на все три состояния. Детали теста — §10.6, Slice 14 (§12).
6. Технически в коде это можно выразить так, что сам флаг `VITE_DIPLOID_GENETICS_ENABLED` **не читается вообще** нигде вне `OverhaulApp`-ветки — тогда «читается, но игнорируется в Classic» превращается в «физически не имеет эффекта в Classic по построению», что надёжнее одной лишь договорённости не читать его там.
7. **Сохранение с новыми полями безопасно открывается при выключении Genetics V2.** Прямое требование, совпадающее с уже сформулированным в проходе 1 (§4 предыдущей версии) — новые поля (`pollen`, `nurseryTray`, `labLevel`, `genomeV2`, обучающие флаги §6.2) существуют в типе `GameState`/`Specimen` всегда, но код legacy-режима их просто не читает и не пишет; при этом они физически не удаляются и не портятся, если игрок переключит флаг обратно на V2 позже.
8. **`main` не изменяется** — сохраняется прямое ограничение задания, актуальное для всех проходов этой работы, не только для этого документа.

## 10. Список необходимых тестов

Раздел переписан относительно прохода 1: явное требование владельца — **не смешивать разные проверки в одну симуляцию фиксированной пары родителей**. Три статистических набора строго разделены.

### 10.1. Unit — диплоидная модель (без изменений по существу относительно прохода 1)
- Разрешение фенотипа по таблице доминирования — по локусу или параметризованно по всем 9 локусам.
- Кодоминантные пары (если определены для Gate 1) — конкретный заявленный случай.
- Гомозиготный локус выражается однозначно.
- Наследование аллеля: при известном rng — ровно один из двух аллелей соответствующего родителя, не третье значение (не пул).
- `speciesId` потомка всегда равен `speciesId` Seed Parent, независимо от rng — прямой тест на «species не наследуется как рядовой локус».
- **Видимость скрытой генетики (новое в проходе 4, §6.1)**: резолвер простой карточки никогда не возвращает скрытый аллель ни в каком поле; резолвер расширенной карточки без раскрытия возвращает второй аллель как `"Не исследован"` (символическое значение, не реальный аллель); после раскрытия (флаг на `Specimen`) резолвер возвращает реальное значение и доминирование; кодоминантные локусы никогда не помечаются как «нераскрытые» (у них нет скрытого состояния по определению).

### 10.2. Unit — mutation roll / pity (переписано под новую модель)
- Обычное наследование (без mutation roll) **никогда** не производит значение, отсутствующее у обоих родителей — тест, специально фиксирующий отсутствие старого `GENE_MUTATE_CHANCE`-поведения в V2 (регрессионный тест «на удаление» старой механики, важен именно потому, что легко случайно скопировать старую функцию по привычке).
- Полная 10-шаговая таблица шансов mutation roll — параметризованный тест на каждую из 10 строк.
- Гарантия на 10-й попытке — детерминированный тест.
- Pity сбрасывается **только** при успешном mutation event — тест, что серия обычных (без мутации) скрещиваний подряд не сбрасывает счётчик преждевременно.
- `speciesId` никогда не меняется мутацией — тест на большой выборке (не единичный ролл): среди N успешных mutation-событий подряд ни одно не меняет `speciesId` потомка.
- Выбор конкретного `mutationId` при успешном ролле — только из каталога, соответствующего выбранному тиру (§9) — тест на корректность фильтрации по тиру.
- **Микроскоп — фильтрация доступных признаков (новое в проходе 4, §6.1)**: список выбора включает только признаки с реально нераскрытым скрытым аллелем; уже раскрытые (микроскопом или естественно) и кодоминантные признаки исключены из списка; попытка раскрыть недоступный признак отклоняется на уровне логики, не только UI; при пустом списке доступных признаков пыль не списывается (тест явно проверяет, что баланс пыли не меняется).

### 10.3. Три раздельных статистических теста (прямое требование владельца)

**Тест 1 — Mendelian inheritance.** **Исправлена статистическая терминология в проходе 5 (§0.4 п.4) — генотип и фенотип перепутаны не были, но были сведены в одно число там, где это два разных распределения:**
- Фиксированная пара гетерозиготных родителей (один и тот же локус, известный заранее, `Aa × Aa`).
- **Генотипы** потомства ожидаются в соотношении **25/50/25** (`AA` / `Aa` / `aa` — гомозигота-доминант / гетерозигота / гомозигота-рецессив, стандартное менделевское расщепление для одного локуса при скрещивании двух гетерозигот). Это распределение **пар аллелей**, не то, что видит игрок.
- **Фенотипы** потомства при **полном доминировании** (единственная модель доминирования в Gate 1 — §6.1 GDD v3, `docs/GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md` §4.3) ожидаются в соотношении **75/25** (доминантный фенотип, объединяющий `AA` и `Aa` / рецессивный фенотип `aa`) — классическое менделевское 3:1. Соотношение фенотипов **25/50/25 было бы верно только при кодоминировании** (три различимых фенотипа на три генотипа один-к-одному) — а кодоминирование в Gate 1 явно не используется (§4.3 `GENETICS_GATE1_IMPLEMENTATION_CONTRACT.md`: «таблица доминирования не содержит кодоминантных записей»). Тест обязан проверять **оба** распределения раздельно, явно поименованными проверками (`genotype distribution` и `phenotype distribution`), не одним ассертом на одно число — чтобы будущий читатель теста не принял 75/25 за баг и не «исправил» его обратно на 25/50/25.
- Seeded RNG (`mulberry32`, тот же паттерн, что уже используется в `genetics.test.ts:34-46`).
- Цель теста — только проверка корректности передачи и выражения аллелей, **без** участия mutation roll (либо шанс мутации отключается на время этого теста, либо выборка достаточно большая, чтобы не искажать статистику наследования — конкретный технический приём выбирается на этапе реализации).

**Тест 2 — Mutation/pity.**
- Последовательные серии попыток (не одна фиксированная пара — здесь важна последовательность вызовов `breed()` с накоплением `pityCounter`, не параллельные независимые испытания).
- Проверка каждой из 10 ступеней pity-кривой по отдельности (не только конечных точек 1 и 10).
- Гарантия на 10-й попытке — детерминированная проверка.
- Среднее ожидание количества попыток до мутации — статистическая проверка близости к **≈7.85** на достаточно большой серии (число из xlsx, §4.2), с разумным допуском.

**Тест 3 — Rarity calibration.**
- **Репрезентативно сгенерированная популяция родителей** — не одна фиксированная пара (в отличие от Теста 1). Означает: родители для скрещиваний в этом тесте сами должны быть результатом предварительной генерации/скрещиваний со случайным разбросом генотипов, чтобы получить распределение результатов, которое отражает игровую популяцию, а не искусственно завышенную/заниженную редкость одной конкретной пары.
- **100 000 результатов** — прямое количественное требование задания (в проходе 1 в коде такого теста не было вовсе, ближайший аналог — 4000 испытаний с допуском ±5% на другую метрику, аудит §13).
- Целевое распределение **50/30/14/5/0.9/0.1%** по тирам Common/Uncommon/Rare/Epic/Legendary/Mythic.
- Детерминированный seed — воспроизводимость обязательна.

### 10.4. Unit — save-миграция (расширено под §7)
- Каждый из 9 пунктов §7 — отдельный тест: гомозиготная фикция для видимых признаков, отсутствие случайной генерации скрытых аллелей, нейтральный дефолт для новых локусов (семантические ID, §7 п.3), визуальная идентичность до/после (сравнение отрендеренного фенотипа), `unknown`/`null` родословная у мигрировавших specimens.
- Тест критерия «save с историей»: все три условия (`specimens.length>2`, `pityCounter>0`, `geneticDust>0`) по отдельности достаточны — параметризованный тест на каждое условие в изоляции (сохранение, подходящее ровно под одно условие, получает `pollen=24, labLevel=3`, все три обучающих флага `true`).
- Тест «нетронутый save»: ни одно условие не выполняется → `pollen=0, labLevel=1`, все три обучающих флага `false`, `pityCounter=0`.
- **Миграционная матрица целиком (новое в проходе 4, §7.1)**: параметризованный тест на все четыре строки таблицы §7.1 (Новый / Нетронутый legacy / Legacy с историей / Уже V2) — каждая строка проверяет все шесть полей (`pollen`, `labLevel`, три флага, `pity`) одновременно, не по отдельности, чтобы поймать возможную рассинхронизацию между полями внутри одного случая.
- **Миграция pity (новое в проходе 4, §6.3)**: параметризованный тест формулы `clamp(floor(existingPityCounter),0,9)` на граничных значениях (0, 5, 9, 10, 15, дробное значение, если оно вообще может встретиться в старых данных) — подтверждает и `clamp`, и `floor`, отдельно друг от друга.
- **Персистентность обучающих флагов (новое в проходе 4, §6.2)**: флаг переключается только после успешно завершённой операции — тест на отменённую/неудачную попытку скрещивания, подтверждающий, что `firstBreedFreeClaimed` остаётся `false`; тест, что повтор обучения из настроек не меняет ни один из трёх флагов; тест, что переключение feature flag (вкл→выкл→вкл) не сбрасывает флаги.
- Идемпотентность: повторный прогон **глобальной миграции** на уже мигрированном сохранении (`SAVE_VERSION>=4`) не меняет `pollen`/`labLevel`/флаги/`pity` повторно (в т.ч. не удваивает грант пыльцы) — тест на строку «Уже V2, все specimens мигрированы» таблицы §7.1.
- Флаг выкл→вкл→выкл→вкл: прогресс, накопленный между переключениями, не затирается (то же требование, что уже было в §4 прохода 1, теперь формально привязано к §7 п.9).
- **`ensureGenomeV2Sidecars` — пять обязательных тестов (новое в проходе 5, §7.2, исправляет дефект прохода 4):**
  1. **Полная миграция V3→V4**: save на `SAVE_VERSION=3` с N specimens без `genomeV2` → после загрузки `SAVE_VERSION=4`, save-уровневые поля мигрированы по матрице §7.1, **и** все N specimens получили sidecar за тот же проход загрузки (проверяет, что оба механизма §7.2 действительно вызываются последовательно в рамках одной загрузки, не только по отдельности).
  2. **V4-save с одним specimen без sidecar**: `SAVE_VERSION=4`, save-уровневые поля уже финальные, ровно один specimen из нескольких не имеет `genomeV2` → после загрузки только этот один specimen получает sidecar; save-уровневые поля (`pollen`/`labLevel`/флаги/`pity`) не меняются ни на йоту (тест именно на то, что механизм 1 не перезапускается только потому, что механизм 2 нашёл работу).
  3. **V4-save со смешанным массивом specimens** (часть с `genomeV2`, часть без, в любом порядке массива) → после загрузки все specimens имеют sidecar; у specimens, которые уже имели `genomeV2` до загрузки, значение поля **побайтово идентично** значению до загрузки (не пересчитано, не переупорядочено внутри).
  4. **V2→Legacy breed→V2 (сценарий §7.2 целиком)**: смоделировать точный сценарий — save мигрирует в V4, флаг Genetics V2 выключается, создаётся новый specimen через legacy `breedSpecimens`/`randomGenome` (не имеет `genomeV2`), флаг включается обратно, save загружается → новый specimen получает корректный sidecar через гомозиготную миграцию его legacy `genome`, старые specimens не затронуты.
  5. **Повторный backfill не меняет существующие sidecars**: вызвать `ensureGenomeV2Sidecars` дважды подряд на одном и том же state (без промежуточных изменений) → результат второго вызова идентичен результату первого на уровне ссылок/значений для specimens, у которых sidecar уже был; количество созданных на втором проходе sidecars — ровно 0, если первый проход уже покрыл все specimens.
  6. **Миграция `mutationId` (новое в проходе 6, §0.5, исправляет дефект implementation contract §4.4)**: параметризованный тест на всех пяти значениях `genome.mutationId` (`golden_vein`, `stardust`, `prism`, `phoenix`, `null`) → `genomeV2.mutationId` мигрировавшего specimen побайтово равен исходному legacy-значению в каждом из пяти случаев. Отдельный тест на неизвестный/повреждённый `mutationId` (строка, не входящая в каталог) → загрузка save не падает, `specimen.genome.mutationId` остаётся неизменным, `genomeV2.mutationId` для этого specimen — `null`. Оба теста дополнительно проверяют, что `pityCounter` и save-уровневые поля не изменились в результате backfill (§7.2 — механизм 2 не читает и не пишет pity).
