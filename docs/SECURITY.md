# Genesis Garden — модель безопасности

## Принцип

Сервер (Supabase Postgres) — единственный источник истины для экономики и генетики. Клиент не может:

- подтвердить, что урожай созрел (`harvest()` пересчитывает по `planted_at`/`grow_seconds`/бустам сам, не веря клиентскому таймеру);
- назначить себе сумму начисления (все суммы — из `seed_catalog`/констант в SQL, не из параметров запроса);
- выбрать результат скрещивания (RNG — `random()` внутри PL/pgSQL, клиент узнаёт результат только из ответа функции);
- изменить свой/чужой `pity_counter` напрямую (только через `breed()`);
- применить чужой ускоритель (`entitlements` читаются по `auth.uid()`, потолок 25% считает сервер);
- присвоить себе чужое растение (`plants`/`gardens` фильтруются по `garden_id`, который сервер сам вычисляет из `auth.uid()` — никогда не принимается от клиента);
- выдать себе покупку (`grant_purchase` недоступен роли `authenticated` вообще — только `service_role`, см. ниже).

## Слои защиты (проверены тестами, не только продекларированы)

1. **GRANT на уровне SQL:** `REVOKE INSERT, UPDATE, DELETE ... FROM authenticated` на все игровые таблицы. Даже если бы RLS был неверно написан, прямой `UPDATE public.gardens ...` от имени игрока падает с `insufficient_privilege` до того, как Postgres вообще посмотрит на политику RLS. Проверено тестом `PASS: прямой UPDATE gardens запрещён`.
2. **RLS (Row Level Security):** каждая таблица — `SELECT` только своих строк (`owner_id = auth.uid()` либо через связанный `garden_id`). Проверено тестом `PASS: A не видит сад B напрямую`.
3. **SECURITY DEFINER RPC с проверкой владения внутри:** каждая функция сама вычисляет `garden_id` из `auth.uid()` и явно проверяет, что переданные `plant_id`/`plot_index` принадлежат ЭТОМУ саду, прежде чем что-либо менять. Проверено тестом `PASS: breed() отклоняет чужое растение`.
4. **EXECUTE-гранты на функции:** отозваны у `anon`/`public` для всех игровых RPC — гость без сессии не может даже попытаться вызвать `harvest()`. Проверено тестом `PASS: anon не может вызывать harvest()`. `grant_purchase` — исключение в обратную сторону: доступен только `service_role` (платёжный webhook), явно отозван даже у `authenticated`. Проверено тестом `PASS: grant_purchase недоступен для authenticated`.
5. **Идемпотентность (`request_log`):** защищает не от чужого доступа, а от двойного списания/начисления при повторной отправке (плохая сеть, двойной клик, ретрай webhook). Проверено тестами повторного `harvest()` и повторного `grant_purchase()`.

## Секреты

- `VITE_SUPABASE_ANON_KEY` — публичный ключ, безопасен в клиентском бандле ТОЛЬКО при корректной RLS (см. выше) — без неё это критическая уязвимость, поэтому RLS обязателен на каждой таблице без исключений (проверяется тестом `run_local.sh`).
- `service_role` key, Paddle API key/webhook secret — никогда не попадают в клиентский код, `git`, или логи GitHub Actions. Хранятся в GitHub Actions Secrets / Supabase Edge Function secrets. `.env.example` содержит только плейсхолдеры, реальный `.env.local` — в `.gitignore`.
- Платёжный webhook (Этап 7) обязан проверять подпись запроса от Paddle до вызова `grant_purchase` — реализуется в Edge Function, а не в этой SQL-функции (SQL уже сам по себе недоступен снаружи, но подпись всё равно проверяется на входе в Edge Function, чтобы никто не мог дёрнуть сам webhook URL с поддельным payload).

## Известные ограничения (честно, не скрыто)

- Один сад на игрока (нет мульти-сада) — упрощение MVP, не проблема безопасности.
- `pollen`/`cutting` как типы подарков заведены в схеме (`CHECK` на `gift_transactions.item_type`), но RPC `send_gift` пока принимает только `plant`/`dust` — нет ресурса под них в игре. Задокументировано в `docs/ECONOMY.md`.
- Дублирование констант баланса между `config.ts` (клиент) и SQL-функциями (сервер) — при рассинхронизации сервер побеждает (авторитетен), но клиентский UI может временно показывать неверную цифру до правки. См. `docs/ECONOMY.md`.
- RLS-тесты прогонялись на локальной голой PostgreSQL с шимом схемы `auth` (нет Docker в песочнице разработки для полноценного `supabase start`) — перед реальным продакшеном нужно ещё раз прогнать `supabase test db` на настоящем Supabase-стеке (см. `docs/TESTING.md`, `docs/DEPLOYMENT.md`).
