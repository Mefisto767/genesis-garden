## 0. Топология: где живёт генетика

Ветка `visual-overhaul` добавляет только презентационный слой (`EstateScene`/`LaboratoryScene` вместо `GardenScene`, Люми, блюпринт мира). Игровая модель не тронута:

- `apps/web/src/App.tsx` — точка входа-переключатель: `VISUAL_OVERHAUL_ENABLED ? <OverhaulApp/> : <ClassicApp/>` (флаг `game/featureFlags.ts:8-9`, читает `VITE_VISUAL_OVERHAUL_ENABLED`).
- `apps/web/src/overhaul/OverhaulApp.tsx:182-194` монтирует те же `LabPanel`/`AlbumPanel`, что и `apps/web/src/ClassicApp.tsx`, без изменения их пропсов (кроме `fullscreenReveal` — только CSS-модификатор, см. §5).
- И `ClassicApp`, и `OverhaulApp` читают один и тот же синглтон `gameStore` (`game/store.ts:362`) через `useGameState()` (`game/useGameState.ts`).

Вывод: генетика, экономика скрещивания и save-формат **идентичны** между `main`/`beta-ready` и `visual-overhaul` — ветка их не переписывала. Всё нижеописанное верно для обоих режимов рендера.

## 1. Полный путь скрещивания: от UI до store и сохранения

Шаги (Classic и Overhaul идентичны, отличается только точка входа в панель):

1. **Вход в лабораторию.**
   - Classic: кнопка «Лаборатория» в `ui/HUD.tsx:48-50` → `setPanel('lab')` в `ClassicApp.tsx`.
   - Overhaul: клик по hotspot «Рабочий стол» в `game/scenes/LaboratoryScene.ts:64-74,140-148` → эмит `overhaulEvents.emit('openHotspot', {hotspot:'workbench'})` → в `OverhaulApp.tsx:140-143` `setPanel('lab')`. Переход в саму лабораторию — отдельная Phaser-сцена (`this.scene.start('Estate')`/вход через клик по зданию, вне рамок генетики).
   - Обе ветки рендерят один и тот же `ui/LabPanel.tsx`.

2. **Выбор двух родителей.** `LabPanel.tsx:69,80-87`: `selected: string[]`, `toggle(id)` — клик по `.specimen-card` в сетке `specimens.map(...)` (`LabPanel.tsx:224-238`). Максимум 2 одновременно выбранных (третий клик заменяет более раннего — `LabPanel.tsx:82-86`). Оба родителя выбираются из одного и того же списка `state.specimens` — **нет разделения на «свой список» и «список родителя B»**: интерфейс Seed Parent / Pollen Parent из GDD не существует, оба родителя выбираются симметрично из своей же коллекции (см. §7).

3. **Опциональная блокировка гена (Этап 5).** `LabPanel.tsx:240-278`: `<select>` с 7 вариантами `LockableGene` (`shape`,`primary`,`secondary`,`leaf`,`pattern`,`size`,`aura`, метки `LOCKABLE_GENE_LABELS:43-51`) + выбор источника (`lockSource: 'a'|'b'`). Кнопка «Скрестить» дизейблится, если пыли не хватает на цену блокировки (`canAffordLock`, `LabPanel.tsx:91,138,275-277`).

4. **Клик «Скрестить».** `doBreed()` (`LabPanel.tsx:93-117`):
   - собирает `GeneLock | undefined` из состояния UI;
   - трекает `track('first_breed_started')` при первой попытке на устройстве (`localStorage['genesis-garden-first-breed-v1']`, `LabPanel.tsx:10-24`);
   - вызывает `gameStore.breedSpecimens(selected[0], selected[1], lock)`.

5. **`GameStore.breedSpecimens(idA, idB, lock?)`** (`game/store.ts:279-303`):
   - `idA === idB` → `null` (отклонение, покрыто тестом `store.test.ts:96-101`);
   - оба id должны существовать в `state.specimens`;
   - `coins < BREED_COST (=12)` → `null`;
   - `geneticDust < lockCost` (если lock задан, `lockCost = BREEDING_CONFIG.dustCostPerLockedGene = 8`) → `null`, **весь breed отклоняется целиком, частичного списания нет** (комментарий `store.ts:273-278`, тест `store.test.ts:172-184`);
   - вызывает чистую функцию `breed(a.genome, b.genome, state.pityCounter, this.rng, lock)` из `game/genetics.ts:114-164` (детали — §4);
   - создаёт `Specimen = { id: nextId(), genome: result.genome, createdAt: Date.now() }` (`nextId()` — `store.ts:20-24`, монотонный счётчик + `Date.now()`, **не UUID**);
   - списывает `BREED_COST` монет, начисляет `dustGained - lockCost` пыли (`dustGained` — случайное целое `[DUST_REWARD_MIN..DUST_REWARD_MAX] = [2..5]`, `store.ts:289-290`), обновляет `pityCounter = result.nextPityCounter`, добавляет specimen в `state.specimens`, продвигает квест `'breed'` (`advanceQuestProgress`, `quests.ts:32-43`);
   - вызывает `this.emit()` → `persist()` (запись в `localStorage`) + уведомление подписчиков React.

6. **Reveal.** `LabPanel.tsx` переходит в режим `result`: сразу рисует `SpecimenThumbnail` (canvas-рендер уже готового генома, §6) в невидимом состоянии, затем через `requestAnimationFrame` + `setTimeout(60ms)` (или мгновенно при `prefers-reduced-motion`) показывает редкость/мутацию/полученную пыль (`LabPanel.tsx:106-116,178-193`). **Никакого отдельного полноэкранного `RevealScene`-компонента с камерой/затемнением нет** — `fullscreenReveal` в Overhaul-режиме лишь добавляет CSS-класс `sheet-reveal-scene`/`lab-reveal-scene` к тем же DOM-узлам (`LabPanel.tsx:36-40,141,145,148,159-167`), логика `doBreed()` не меняется.

7. **Дальнейшая судьба specimen.** Новый specimen сразу попадает в `state.specimens` — **это финальный, полностью выраженный геном**, готовый к показу в альбоме. Никакого «посева гибридного семени» и последующего выращивания не происходит (см. §9 — это ключевое структурное расхождение).

Итог сохраняется через `persist()` (`store.ts:162-169`) в `localStorage['genesis-garden-save-v1']` как `JSON.stringify({...state, version: SAVE_VERSION})`.

## 2. Формат генома

`interface Genome` (`game/genetics.ts:36-45`):

```ts
interface Genome {
  shape: number;        // 1-8, диапазон GENETICS_CONFIG.shapes
  primary: string;      // hex-цвет из PRIMARY_POOL (8 значений)
  secondary: string;    // hex-цвет из SECONDARY_POOL (7 значений)
  leaf: string;         // hex-цвет из LEAF_POOL (3 значения)
  pattern: 'solid' | 'duotone';
  size: 'small' | 'normal' | 'large' | 'giant';
  aura: 'none' | 'faint' | 'glow' | 'radiant';
  mutationId: string | null;
}
```

Это **плоская структура из 8 полей, по одному значению на поле** — не диплоидный набор аллелей. Ни для одного поля не хранится пара «унаследованных» значений, скрытого/видимого состояния или ссылки на родителя. Инвариант `pattern==='solid' ⟹ secondary===primary` обеспечивается на месте создания (`randomGenome`, `genetics.ts:73`) и на месте скрещивания (`breed`, `genetics.ts:146`).

Комментарий в начале файла (`genetics.ts:1-21`) сам документирует расхождение с ТЗ: «8 параметров из ТЗ реализованы так, чтобы каждый был РЕАЛЬНО читаем в текущем арт-паке» — `shape` одновременно исполняет роль и «вида» (species), и одного из 8 генов; отдельных локусов «стебель», «форма листа», «форма цветка/крона», «узор» (как геометрии) не существует — `pattern` не геометрический узор, а бинарный переключатель monochrome/contrast поверх `mask_secondary` (см. §6).

Поле в `types.ts:18-29` `Specimen`:
```ts
interface Specimen {
  id: string;             // spec_<base36-timestamp>_<counter>, store.ts:21-24
  genome: Genome;
  createdAt: number;      // Date.now()
  favorite?: boolean;     // опционально, добавлено Этапом 5, миграции SAVE_VERSION не потребовало
}
```

## 3. Виды, гены и их фактическая реализация

### 3.1. «Вид» (species)

Ассетов подготовлено 8 (`plant_species01`…`plant_species08`, `public/assets/plants/`, по 3 стадии × 4 слоя + `_ref` на каждый — подтверждено `find`, 8×3×5=120 файлов). Но в **игровой экономике** (`config.ts:29-33`, `SEED_BALANCE`) заведено только 3 семени:

| id | speciesId | growMs | buyCost | sellValue |
|---|---:|---:|---:|---:|
| `sprout` | 1 | 60 000 (1 мин) | 5 | 8 |
| `common` | 2 | 900 000 (15 мин) | 15 | 35 |
| `upgraded` | 5 | 7 200 000 (2 ч) | 60 | 170 |

Виды 3, 4, 6, 7, 8 не имеют семени в магазине (`ui/ShopPanel.tsx` рендерит только `SEED_CATALOG`, `seedCatalog.ts:15-23`, который прямо мапится из `SEED_BALANCE`) — единственный способ увидеть их в игре — если `shape`-ген мутирует в это значение при скрещивании (§4). Нет привязки «Солнечник»/«Колокольник»/… к конкретному `speciesId` где-либо в коде — имена видов из GDD в коде не встречаются (проверено `grep -ri "солнечник\|колокольник\|бархатн\|туманн\|кактус"` — 0 совпадений в `apps/web/src`).

### 3.2. Восемь «генов» — фактический список (не соответствует таблице локусов GDD)

| Поле генома | Тип | Кол-во значений | Что визуально меняет |
|---|---|---:|---|
| `shape` | число 1-8 | 8 (`GENETICS_CONFIG.shapes`, `config.ts:58`) | выбирает арт-пак вида целиком (силуэт, лист, цветок — всё сразу одной сменой ассета) |
| `primary` | hex | 8 (`primaryPool`, `config.ts:59`) | тонирует `mask_primary` |
| `secondary` | hex | 7 (`secondaryPool`, `config.ts:60`) | тонирует `mask_secondary`, форсируется = `primary` при `pattern==='solid'` |
| `leaf` | hex | 3 (`leafPool`, `config.ts:61`) | тонирует `mask_leaf` |
| `pattern` | enum | 2 (`solid`/`duotone`) | не геометрия — переключатель «монохром / контрастный доп.цвет» |
| `size` | enum | 4 различных значения, но пул из 5 слотов с весами `['small','normal','normal','large','giant']` (`config.ts:62`) — `normal` вдвое вероятнее остальных | масштаб спрайта (`sizeScale`, `genetics.ts:184-186`: 0.75/1/1.25/1.55) |
| `aura` | enum | 3 различных значения, пул из 6 слотов `['none','none','none','faint','faint','glow']` (`config.ts:63`) — `radiant` **не входит в пул рождения**, достижим только через мутацию/лок | CSS/canvas box-shadow вокруг миниатюры (`auraGlowStyle`, `specimenRender.ts:87-98`); в самой Phaser-сцене свечение не рендерится (`buildPlantSprite`, `plantArt.ts:32-57`, не читает `aura`) |
| `mutationId` | строка\|null | 4 фиксированных значения (§4.4) | форсирует минимальную редкость и подпись «✦ Особая мутация» |

Локусов «Стебель», «Цветок/крона», «Узор» (в смысле геометрического паттерна: пятна/полосы/звёзды/жилки/градиент) как отдельных измерений **не найдено в коде** — покрыты частично `shape` (весь силуэт целиком) и `pattern` (не геометрия).

### 3.3. Наследование

`gene<T>(pa, pb, pool, key?)` (`genetics.ts:125-137`), общая функция для всех 7 наследуемых полей (`mutationId` не наследуется — вычисляется отдельно, §4.4):

```
если задан lock на этот ген → взять значение зафиксированного родителя, без ролла
иначе:
  shouldMutate = rng() < GENE_MUTATE_CHANCE(0.08)
                 || (forceGeneMutation && !forcedOnce && rng() < pityMutationChance(0.7))
  если shouldMutate → взять случайное значение из пула (mutated=true, forcedOnce=true)
  иначе → inherit(pa, pb, rng) = rng()<0.5 ? pa : pb   (genetics.ts:65-67)
```

Это **не диплоидное наследование с доминированием**: у гена нет двух аллелей и приоритета — есть ровно одно текущее значение, которое либо копируется 50/50 от одного из двух родителей, либо (редко) заменяется случайным значением из пула. Нет понятия «скрытый аллель», «видимый признак», «доминантный/рецессивный/кодоминантный». Родитель, чьё значение не выбралось, не оставляет никакого следа в потомке — унаследовать «спрятанный» ген от родителя, у которого он не был выражен, невозможно в принципе, потому что у родителя тоже хранится только одно выраженное значение на поле.

### 3.4. Межвидовое скрещивание

Отдельного правила «Seed Parent задаёт вид, Pollen Parent передаёт обычные аллели в универсальные слоты» **не найдено в коде**. `shape` — рядовое поле генома, наследуется той же функцией `gene()`, что и все остальные: 50/50 от любого из двух родителей (без привязки к порядку выбора `selected[0]`/`selected[1]` как «seed»/«pollen» — оба переданы в `breed(a, b, ...)` симметрично, `store.ts:288`) либо мутация в случайное значение 1-8. Потомок межвидового скрещивания может получить вид, которого не было ни у одного родителя (если сорвалась мутация `shape`), и с равной вероятностью получить любой из 8 видов независимо от «домашнего» вида родителей — деления на «внутривидовое / межвидовое» скрещивание с разной механикой в коде нет вообще (в частности, нет и разной цены — см. §8).

## 4. RNG, мутации, pity, редкость

### 4.1. RNG

`game/rng.ts`: единственный источник случайности в игровой модели — инжектируемый `RngFn = () => number`. `mulberry32(seed)` (`rng.ts:8-17`) — детерминированный PRNG для тестов; `defaultRng = () => Math.random()` (`rng.ts:20`) — источник по умолчанию в проде. `GameStore` принимает `rng` в конструкторе (`store.ts:139,143`) и передаёт один и тот же экземпляр во все вызовы `breed()`/`randomGenome()` внутри стора — сам breed детерминирован при фиксированном rng и входных геномах (подтверждено тестом `genetics.test.ts:48-53`).

Серверная копия (`supabase/migrations/20260827120200_functions.sql`, см. §12) использует Postgres `random()` напрямую — не тот же генератор, недетерминирован, не сидируется с клиента.

### 4.2. Шанс мутации гена — фактическая формула

**Нет эскалирующей 10-шаговой кривой из GDD (3%→4%→…→11%→100%).** Фактически: `GENE_MUTATE_CHANCE = 0.08` (`config.ts:55`) — **один и тот же фиксированный шанс на каждый из 7 генов при каждом скрещивании**, независимо от того, сколько скрещиваний прошло с последней мутации.

Единственный элемент, зависящий от счётчика попыток — это **pity-форсирование**, а не наращивание базового шанса:

```
forceGeneMutation = pityCounter >= PITY_THRESHOLD (=10)   // genetics.ts:122
```
Если `forceGeneMutation` истинно, то **первый** ген в порядке перебора (`shape → primary → secondary → leaf → pattern → size → aura`, `genetics.ts:139-145`), у которого сработает `rng() < pityMutationChance(0.7)` (проверяется только если обычный 8%-ролл для этого гена не сработал), гарантированно мутирует; после первого форса (`forcedOnce=true`) остальные гены форсу больше не подлежат — работают только по своему обычному 8% шансу (`genetics.ts:129-133`).

Итог: `pityThreshold=10` даёт **не 100%-гарантию мутации на 10-й попытке** в буквальном смысле (гарантирован только форс-ролл с вероятностью 70% на первом подходящем гене, суммарно с обычным шансом ≈ выше, но не строго 1.0) — статистика ниже.

Статистический unit-тест (`genetics.test.ts:173-190`) проверяет только базовый (не-pity) режим на 4000 испытаниях, допуск ±5% вокруг `1-(1-0.08)^7 ≈ 44.0%` (комментарий в тесте это явно проговаривает). **Ни один тест не проверяет 100 000 скрещиваний**, и ни один тест не проверяет статистику именно pity-режима (`pityCounter>=10`) — есть только детерминированный (не статистический) тест, что pity форсирует мутацию хотя бы одного гена при специально подобранном rng (`genetics.test.ts:109-124`).

### 4.3. Pity

- `pityCounter` — единственный, глобальный (`GameState.pityCounter`, `types.ts:57`), не привязан к виду — совпадает с духом GDD «Pity принадлежит аккаунту».
- Сброс: `nextPityCounter = mutated ? 0 : pityCounter + 1` (`genetics.ts:149`) — сбрасывается при **любой** мутации гена (в т.ч. случайной 8%-ной, не только pity-форсированной), не только при «настоящей» мутации-трейте.
- Виден игроку: `LabPanel.tsx:139,212-216` — «До гарантированной мутации гена: N скрещиваний» либо «уже готова», где N = `GENETICS_CONFIG.pityThreshold - pityCounter`.
- Оплата/платность: `breedSpecimens` не принимает и не проверяет никаких платёжных данных (подтверждено чтением всей сигнатуры `store.ts:279`) — платить за pity нельзя, это верно и в коде, не только в GDD.

### 4.4. Именная мутация (`mutationId`)

Каталог — 4 записи, `MUTATIONS_CONFIG` (`config.ts:73-78`):

| id | name | minRarity |
|---|---|---|
| `golden_vein` | Золотая жилка | rare |
| `stardust` | Звёздная пыльца | epic |
| `prism` | Призма | epic |
| `phoenix` | Феникс | legendary |

Роллятся так (`genetics.ts:152-160`):
```
mutationId = null
если mutated (хотя бы один ген мутировал в этом скрещивании) и rng() < MUTATION_CHANCE(0.06):
    mutationId = случайный элемент MUTATIONS
иначе если pityTriggered и mutationId ещё null и rng() < pityTraitChance(0.35):
    mutationId = случайный элемент MUTATIONS
```
Нет тиров Minor/Major/Signature/Mythic, нет весов 70/25/5%, нет отдельного пространства «20–25 коллекционных мутаций» — ровно 4 жёстко заданных id, выбираемых равновероятно (`pick(MUTATIONS, rng)`, `genetics.ts:61-63`) при попадании в любую из двух веток ролла выше. Нет тира `mythic` — сам тип `RarityTier` (`genetics.ts:30`) перечисляет только `'common'|'uncommon'|'rare'|'epic'|'legendary'`, пятого шага нет физически в типе.

### 4.5. Редкость (`rarityOf`)

`genetics.ts:166-182` — не роллится отдельно и не имеет фиксированных базовых процентов (50/30/14/5/0.9/0.1 из GDD в коде не участвуют ни в одном вычислении). Это детерминированная функция итогового генома:

```
если mutationId задан → rarity = minRarity этой мутации (жёсткий пол)
иначе — очковая система (RARITY_SCORING, config.ts:81-91):
  giant: +2, large: +1
  aura radiant: +3, glow: +2, faint: +1
  pattern duotone: +1
  score>=5 → epic; score>=3 → rare; score>=1 → uncommon; иначе common
```
Максимально достижимый score без мутации — `giant(2)+radiant(3)+duotone(1)=6`, что даёт `epic` (порог epic=5 достигается раньше максимума) — **`legendary` без мутации в принципе недостижим** (порог для legendary в очковой системе не определён вовсе — только через `mutationId`). Границы подтверждены тестами `genetics.test.ts:193-224`.

## 7. Посадка и рост результата скрещивания

Прямая проверка: `ui/PlantPicker.tsx` — единственный компонент, вызывающий `gameStore.plantSeed(plotId, seedId)` (`:47`) — работает **исключительно** со списком `SEED_CATALOG.filter(seed => (inventory[seed.id] ?? 0) > 0)` (`:15`), то есть только с тремя магазинными семенами по `inventory[seedId]`. Тип `Specimen` (продукт скрещивания) не имеет `seedId` и никогда не попадает ни в `inventory`, ни в список, доступный `PlantPicker`.

Геном становится известен игроку сразу и полностью в момент клика «Скрестить» (см. §1, шаг 6) — стадии роста растения (`stage` 1-3 в рендере) относятся только к магазинным семенам с фиксированным `PlantColorway`, не к специменам с геномом. `Nursery Tray` (питомник до 8 невыращенных гибридов) как структура данных или UI **не найден в коде** ни в `types.ts`, ни в каком-либо `.tsx`/`.ts` файле (проверено `grep -ri "nursery\|питомник"` по `apps/web/src` — 0 совпадений в игровом коде; слово «питомник» встречается только в GDD-текстах, скопированных в `docs/FINAL_VISION.md`).

## 8. Что происходит с растением/специменом после «сбора»

Два разных объекта путаются в GDD и различаются в коде:

- **Магазинное растение на грядке** (`Plot`, `types.ts:31-36`): `harvest(plotId, now)` (`store.ts:249-266`) начисляет `sellValue` монет и **обнуляет грядку** (`seedId:null, plantedAt:null`) — растение не остаётся на грядке (в отличие от GDD «экземпляр остаётся на грядке»). Никакого specimen/генома при этом не создаётся — это чисто экономический цикл посадка→монеты.
- **Specimen (продукт скрещивания)**: после `breedSpecimens` живёт в `state.specimens[]` бессрочно, до одного из двух явных действий игрока:
  - `toggleFavorite(id)` (`store.ts:329-338`) — чисто клиентский флаг, не влияет на экономику, только защищает от переработки;
  - `recycleSpecimen(id)` (`store.ts:314-326`) — удаляет specimen, начисляет фикс. 5 пыли; отклоняется (`'favorite'`), если specimen в избранном (`AlbumPanel.tsx:23-33` показывает toast-подсказку).
- Родители при скрещивании **не расходуются и не блокируются** — комментарий `store.ts:268-271` прямо это фиксирует как сознательное упрощение MVP («родители не расходуются... экономику можно добавить на Этапе 4»). Оба родителя можно тут же выбрать снова для следующего скрещивания.
- «Выставить» (витрина/showcase), «дать другу пыльцу карту» — **не реализовано**: нет ни одного store-метода, UI-компонента или SQL RPC с такой семантикой (соцобмен, `ui/SocialPanel.tsx`, работает только с `dust`/`plant`-подарками на уровне «переслать существующий specimen по сети», см. §12, и не пересекается с показом «на витрине»).

## 10. Save schema и миграции

### 10.1. Формат сохранения (клиент, localStorage)

Ключ: `'genesis-garden-save-v1'` (`store.ts:11`, буквальная строка, несмотря на суффикс `v1` в самом имени ключа — версионирование живёт в отдельном поле `version`, не в имени ключа). Текущая `SAVE_VERSION = 3` (`store.ts:12`).

Сохраняемый JSON — весь `GameState` (`types.ts:48-64`) плюс `version`:
```ts
{
  coins: number;
  plots: Plot[];                      // 24 записи, {id,unlocked,seedId,plantedAt}
  inventory: Record<string, number>;  // seedId -> qty
  specimens: Specimen[];              // {id, genome, createdAt, favorite?}
  geneticDust: number;
  pityCounter: number;
  questProgress: Record<string, number>;
  questsClaimed: string[];
  entitlements: Entitlement[];
  version: 3;
}
```

### 10.2. Миграционная логика (клиент)

`loadState(rng, storage)` (`store.ts:55-86`):
- нет сырых данных или невалидный JSON → `createInitialState(rng)` (новая игра, без падения, покрыто тестом `store.test.ts:318-335`);
- базовая структурная проверка (`parsed.plots` массив, `parsed.coins` число) — иначе тоже новая игра;
- `version = parsed.version ?? 1` — сохранения без явного поля `version` трактуются как v1;
- `version < 2`: если нет `specimens` — генерируются 2 стартовых через `randomGenome(rng)` (новые id/createdAt, **не те геномы, что были у игрока, если он вообще играл до Этапа 2** — для настоящих v1-сохранений это добавление случайных специменов, не восстановление истории), дефолты `geneticDust=0`, `pityCounter=0`;
- `version < 3`: дефолты `questProgress={}`, `questsClaimed=[]`, `entitlements=[]`.
- Миграции **только добавляют недостающие поля**, никогда не удаляют/не обнуляют существующие (комментарий `store.ts:63-64`, подтверждено тестом «v2→v3 без потери прогресса», `store.test.ts:273-316`, независимо перепрогнан на этой ветке).
- `favorite?: boolean` в `Specimen` добавлен без изменения `SAVE_VERSION` — необязательное поле, отсутствие читается как `false` (`types.ts:22-28`, комментарий это явно объясняет).

### 10.3. Облачная (Supabase) сторона

Полная схема — в `supabase/migrations/20260827120000_init_schema.sql` (18 таблиц + `seed_catalog`/`request_log`; см. §12 — таблица `plants` хранит `genome jsonb` с CHECK-ограничением ровно на те же 8 плоских ключей, что и клиентский `Genome`, `init_schema.sql:72-76`, `rarity text CHECK IN (5 тиров, без mythic)`, `init_schema.sql:69`).

`migrate_local_progress(p_choice, p_local_state, p_request_id)` (`supabase/migrations/20260827130000_migrate_local_progress.sql`) — перенос localStorage→облако:
- читает из присланного JSON только 4 поля: `coins`, `geneticDust`, `plots[].{id,unlocked}`, `specimens[].genome`;
- **не читает и не переносит**: `pityCounter`, `inventory`, `questProgress`, `questsClaimed`, `entitlements`, а также `id`/`createdAt`/`favorite` у каждого specimen;
- **не проверяет `SAVE_VERSION` вообще** — никакой версионной защиты на серверной стороне миграции нет;
- `merge` берёт `MAX(cloud, local)` по числовым ресурсам (никогда не сумма — явно задокументировано в самом файле);
- дедуп специменов при merge — по текстовому равенству `genome::text` (не по id/хэшу) — специмен с идентичным геномом, но другим id, не переносится повторно;
- клиентская сторона (`sync/migration.ts`, `buildMigrationPayload`, `:74-81`) сама **не отправляет** `pityCounter`/`inventory`/`questProgress`/`questsClaimed`/`entitlements` — то есть потеря этих полей при облачной миграции согласована по обеим сторонам, а не однобокий баг сервера.
- Клиент **не подключён** к этому RPC в реальном геймплее: `game/store.ts` нигде не импортирует и не вызывает `gameApi`/`GameApi` (grep подтверждён) — `sync/gameApi.ts:169-177` сам документирует это как отложенный шаг интеграции. Т.е. серверная генетика (§12) существует, протестирована изолированно, но **не является частью работающего игрового цикла** на этой ветке.

## 12. Серверная (Supabase) генетика — независимый порт

Файл `supabase/migrations/20260827120200_functions.sql`, функция `breed(p_parent_a uuid, p_parent_b uuid, p_request_id uuid)` — построчно совпадает по алгоритму, константам и пулам с клиентским `genetics.ts`/`config.ts` (проверено построчным сопоставлением): те же `breedCost=12`, `pityThreshold=10`, `geneMutateChance=0.08`, `mutationChance=0.06`, `pityMutationChance=0.7`, `pityTraitChance=0.35`, тот же порядок 7 генов, та же схема «первый форс, затем обычный шанс», тот же расчёт `rarity_of()` (те же очки/пороги/тиры, тоже без mythic).

Значимые расхождения сервер↔клиент:
- **У серверной `breed()` нет параметра `lock`** — сигнатура строго 3 параметра (`p_parent_a, p_parent_b, p_request_id`), блокировка гена за пыль реализована только на клиенте.
- `random_genome()` (стартовые специмены) и `rarity_of()` продублированы на PL/pgSQL отдельно от `breed()`, используют встроенный `random()` (не тот же RNG, что клиент, недетерминирован).
- Схема `gift_transactions.item_type` CHECK допускает значения `'pollen'`/`'cutting'` (`init_schema.sql:195`), но ни одна RPC их не принимает — `send_gift()` жёстко ограничена `('plant','dust')` (`functions.sql`, обе версии — Этап 3 и Этап 6) — это задел схемы под будущую пыльцу-как-подарок, не рабочий ресурс.
- Таблица `plants.rarity` CHECK разрешает ровно 5 значений — `mythic` невозможно записать даже гипотетически без миграции схемы.

SQL-тесты (`supabase/tests/02_scenario_tests.sql`) проверяют владение родителями (`parent_not_owned`) и точное списание `breedCost`, но **не проверяют** статистику шанса мутации/pity/распределение редкости — тест явно обходит недетерминированность `random()` через прямую установку `genetic_dust` вместо проверки диапазона награды (задокументировано в самом файле, см. комментарий у соответствующего блока).

Ключевой архитектурный факт: серверная генетика полностью реализована и покрыта тестами **изолированно**, но не вызывается из работающего игрового UI (см. §10.3, последний абзац) — на всех ветках, включая `visual-overhaul`, реальное скрещивание всегда идёт через локальный `GameStore.breedSpecimens`.
