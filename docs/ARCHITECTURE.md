# Genesis Garden — архитектура

## Общая картина

Genesis Garden — статический фронтенд (React + Phaser), который может работать в двух режимах:

1. **Локальный (по умолчанию)** — весь прогресс живёт в `localStorage` браузера, экономика и генетика считаются в клиентском TypeScript-коде (`src/game/`). Никакого backend'а, никакого аккаунта. Это режим, в котором играет обычный бета-тестер сегодня.
2. **Облачный (за feature flag `VITE_CLOUD_SYNC_ENABLED`)** — тот же клиентский код, но все изменяющие действия (посадка, сбор, скрещивание, покупки, подарки...) идут через Supabase RPC вместо прямой мутации локального состояния; сервер — единственный источник истины для экономики.

Оба режима используют одну и ту же игровую модель (`GameStore`) и один и тот же UI — переключение прозрачно для React-компонентов, разница только в том, откуда приходит следующее состояние: из локальной мутации или из ответа RPC.

## Клиент (`apps/web/src`)

- **`game/store.ts`** — синглтон `GameStore`, pub/sub, единственный источник состояния игры для React. Персистится в `localStorage` (`genesis-garden-save-v1`), версионируется (`SAVE_VERSION`, есть миграции схемы сейва между версиями — см. `store.test.ts`).
- **`game/config.ts`** — вся баланс-конфигурация одним объектом (стоимости, тайминги роста, шансы мутаций и т.д.) — источник правды для клиента; сервер зеркалирует те же числа в SQL (см. `docs/ECONOMY.md`, там же зафиксирован технический долг: нет единой таблицы `game_config`, числа приходится синхронизировать вручную в двух местах).
- **`game/genetics.ts`** — геном (8 параметров), `breed()`, `rarityOf()`, pity-счётчик. Принимает инжектируемый `rng`, поэтому детерминированно тестируется (Vitest) и один и тот же алгоритм честно портирован на PL/pgSQL для серверного режима.
- **`game/PhaserGame.ts` + `game/scenes/*`** — сама сцена сада (canvas, сетка грядок, клики). Phaser не знает о React и не хранит состояние сам — только рисует то, что отдаёт `GameStore`, и сообщает о кликах наружу через callbacks.
- **`ui/*.tsx`** — все панели (магазин, инвентарь, лаборатория, альбом, соцобмен, покупки, admin, цели) — обычные React-компоненты поверх `GameStore`/Supabase-клиента.
- **`auth/`** — `AuthGate.tsx` (гость / magic link), `AuthContext.tsx` (глобальный статус сессии, активен только при `VITE_CLOUD_SYNC_ENABLED=true`).
- **`sync/`** — `migration.ts` (перенос локального сейва в облако при первом входе, keep/merge), `offlineQueue.ts` (очередь изменяющих запросов, которые не удалось отправить, дренируется по событию `online`).
- **`payments/`** — `PaymentProvider` интерфейс, `MockPaymentProvider` (полностью рабочий) и `PaddlePaymentProvider` (честно возвращает "не подключено" без реального аккаунта Paddle — не притворяется успехом).
- **`analytics/track.ts`** — единая точка вызова событий, шлёт в Supabase `analytics_events` через RPC `log_analytics_event` (если есть облачная сессия) — локальный режим не логирует ничего (некуда).
- **`admin/adminData.ts`** — чтение агрегатов для read-only admin-дашборда напрямую через уже существующие RLS-политики (`is_admin()`), без отдельных RPC.
- **`pwa/`** — регистрация service worker (`public/sw.js`, stale-while-revalidate, только same-origin GET — не полный precache).
- **`monitoring/errorReporting.ts`** — опциональный Sentry-адаптер: без `VITE_SENTRY_DSN` не делает вообще ничего, даже динамический импорт не вызывается.

## Как React и Phaser делят экран

Игровой canvas (Phaser) рендерится в контейнер под всем React UI. Панели (магазин, лаборатория и т.д.) — обычные DOM-оверлеи поверх канваса. **Важный нюанс, найденный и исправленный на Этапе 9**: Phaser 3 по умолчанию слушает `mousedown`/`click` на всём `window`, а не только на своём канвасе — клики внутри открытой DOM-панели могли "протекать" в игру насквозь, минуя DOM z-index. Решение — `App.tsx` держит `game.input.enabled = !isOverlayOpen` и переключает его в эффекте при открытии/закрытии любой панели/онбординга/модалки посадки. Это единственный способ гарантированно изолировать ввод, задокументировано подробно в `docs/IMPLEMENTATION_STATUS.md` (раздел Этапа 9).

## Сервер (`supabase/migrations`)

Схема — 18+ таблиц (полная карта в `docs/DATA_MODEL.md`). Все изменяющие операции — только через **SECURITY DEFINER RPC**, не через прямые `INSERT`/`UPDATE`/`DELETE` от игрока (роль `authenticated` не имеет прав на запись в игровые таблицы вообще — см. `docs/SECURITY.md`). Список RPC:

- `plant`, `harvest`, `expand_plot`, `buy_seed` — базовый игровой цикл.
- `breed`, `recycle_plant` — генетика.
- `claim_quest`, `advance_quest_progress` (внутренняя) — квесты.
- `send_gift`, `claim_gift`, `decline_gift`, `block_user`, `unblock_user`, `resolve_public_code` — соцобмен.
- `grant_purchase` (только `service_role` — платёжный webhook), `mock_grant_purchase` (для локальной/CI проверки idempotency без реального Paddle).
- `migrate_local_progress` — перенос старого локального сейва при первом входе в аккаунт.
- `log_analytics_event` — запись событий аналитики.

**Идемпотентность:** каждая изменяющая RPC принимает `p_request_id uuid` от клиента и первым делом проверяет `request_log` — повторный вызов с тем же `request_id` (сетевой ретрай, двойной клик, офлайн-очередь, отправившая один и тот же запрос дважды) возвращает сохранённый предыдущий результат, не выполняя действие второй раз. Это единственный механизм защиты от двойной траты, а не UI-дебаунс.

**RLS + GRANT + SECURITY DEFINER** — три независимых слоя защиты, каждый проверен отдельным SQL-тестом, подробности в `docs/SECURITY.md`.

## Тестовая инфраструктура без живого Supabase

В этой среде разработки нет доступа к реальному Supabase-проекту (Docker/Supabase CLI недоступны — см. `docs/AUDIT.md`). Вместо моков — `supabase/tests/00_local_auth_shim_pre.sql` создаёт минимальную имитацию схемы `auth` и ролей `anon`/`authenticated`/`service_role` поверх обычного локального PostgreSQL 16, после чего применяются те же самые миграции (`supabase/migrations/*.sql`) и запускаются сценарные тесты (`02_scenario_tests.sql` и далее) — это не имитация поведения, а выполнение настоящего SQL/RLS/RPC-кода, который дословно попадёт в реальный Supabase-проект. `run_local.sh` — для локальной разработки (`su postgres`), `run_ci.sh` — TCP-вариант для GitHub Actions (`postgres:16` service-контейнер). Подробнее — `docs/TESTING.md`.

## CI/CD

`.github/workflows/ci.yml` — один workflow: `test` (lint → typecheck → vitest → SQL против реального Postgres-сервиса → build → три Playwright e2e) → `deploy` (публикация `dist/` на GitHub Pages при зелёном `test` и push в `main`, plus post-deploy smoke-test). Подробности — `docs/DEPLOYMENT.md`.

## Сознательные ограничения MVP (не забытые, а решённые)

- Один сад на игрока (`gardens` — 1:1 с профилем), не мультисад.
- Баланс дублируется в двух местах (клиент/сервер) вручную — см. `docs/ECONOMY.md`.
- "Узор"/"форма листа" в геноме реализованы как цвет/контраст поверх существующих арт-масок, не отдельной геометрией — задел под будущий арт без изменения движка скрещивания.
- Admin-дашборд агрегирует события клиентски при чтении (до `EVENTS_FETCH_LIMIT=20000` строк) — не рассчитан на промышленный масштаб, честно задокументировано в `docs/ANALYTICS.md` как кандидат на будущую SQL-агрегацию.
