Назначение этого документа — зафиксировать то, что `GENETICS_TARGET_DELTA.md` сознательно оставляет как «вопрос дизайна локусов, не этого документа» (сам delta-документ, §4.1: *«Видимый фенотип локуса — по таблице доминирования (`DOMINANCE_TABLE`, состав — вопрос дизайна локусов, не этого документа)»*). ## 0. Почему девять локусов, не восемь

Существующий legacy-геном (аудит §3.2, `game/genetics.ts:36-45`) хранит `leaf: string` — независимый **цвет** листа (`leafPool`, 3 значения) — отдельно от какой-либо геометрии листа (геометрии формы листа в legacy-коде не существует вовсе). Ранняя 8-локусная формулировка целевой модели (GDD v3, исходная редакция §4.2) объединяла «Лист» в один локус, из-за чего при проектировании миграции независимый цвет листа оказывался либо без собственного места в новой модели (терялся), либо вынужденно смешивался с геометрией формы листа в один локус (переставал наследоваться как отдельное измерение — то есть у потомка цвет и форма листа были бы жёстко связаны, что не соответствует ни legacy-поведению, ни GDD-намерению «форма и расположение листьев» как отдельного визуального измерения от «цвета»).

**Решение**: `leafColor` — самостоятельный, девятый локус, независимый от `leafForm` (формы листа). Оба наследуются по одному и тому же диплоидному механизму, независимо друг от друга. Это единственное содержательное отличие 9-локусной модели от исходной 8-локусной; остальные восемь локусов (`stemForm`, `leafForm`, `flowerForm`, `primaryColor`, `secondaryColor`, `pattern`, `size`, `aura`) сохраняют смысл, приписанный им в `GENETICS_TARGET_DELTA.md` и GDD v3.

Комбинаторика (проверено программно, docs-only симуляция §4.6):

| Локус | Аллелей |
|---|---:|
| `stemForm` | 3 |
| `leafForm` | 4 |
| `flowerForm` | 4 |
| `primaryColor` | 8 |
| `secondaryColor` | 7 |
| `leafColor` | 3 |
| `pattern` | 5 |
| `size` | 4 |
| `aura` | 4 |

`3 × 4 × 4 × 8 × 7 × 3 × 5 × 4 × 4 = 645 120` базовых фенотипов на вид.
`645 120 × 8 видов = 5 160 960` потенциальных фенотипов всего.

Оба числа заменяют устаревшие `138 240`/вид и `1 105 920` всего из 8-локусной формулы — они физически основаны на старом наборе (`3×4×4×8×6×5×3×4=138 240`, где «6» — устаревшее число вторичных цветов, тоже расходившееся с фактическим кодом, аудит §3.2, где `secondaryPool` уже содержит 7 значений, не 6). QA-минимум производственного релиза (25 000 визуально валидных сочетаний) остаётся прежним — он был явно определён как художественный/QA-порог, не как доля от общей комбинаторики, и не зависит от того, восемь локусов или девять.

## 4.1. TypeScript data schema

```ts
/**
 * Пара аллелей одного локуса — ровно по одному от каждого родителя (или два
 * одинаковых значения для гомозиготного/мигрировавшего локуса). Порядок
 * полей `a`/`b` НЕ несёт смысла доминирования — доминирование разрешается
 * исключительно через DOMINANCE_TABLE (§4.3), никогда через порядок.
 */
interface AllelePair<T extends string = string> {
  a: T;
  b: T;
}

// --- девять локусов, ровно эти девять ключей, ни одним больше ---

type StemFormAllele =
  | 'stem_standard' | 'stem_branching' | 'stem_climbing';

type LeafFormAllele =
  | 'leaf_standard' | 'leaf_broad' | 'leaf_narrow' | 'leaf_frilled';

type FlowerFormAllele =
  | 'flower_standard' | 'flower_fan' | 'flower_cap' | 'flower_star';

type PrimaryColorAllele =
  | 'primary_honey' | 'primary_amber' | 'primary_sunset' | 'primary_coral'
  | 'primary_lilac' | 'primary_violet' | 'primary_leaf' | 'primary_frost';

type SecondaryColorAllele =
  | 'secondary_forest' | 'secondary_sunset' | 'secondary_amber'
  | 'secondary_crimson' | 'secondary_purple' | 'secondary_sky' | 'secondary_ochre';

type LeafColorAllele =
  | 'leaf_color_meadow' | 'leaf_color_fresh' | 'leaf_color_forest';

type PatternAllele =
  | 'pattern_solid' | 'pattern_duotone' | 'pattern_spots'
  | 'pattern_stripes' | 'pattern_veins';

type SizeAllele =
  | 'size_normal' | 'size_large' | 'size_small' | 'size_giant';

type AuraAllele =
  | 'aura_none' | 'aura_faint' | 'aura_glow' | 'aura_radiant';

/** Полный диплоидный геном Genetics V2. */
interface GenomeV2 {
  stemForm: AllelePair<StemFormAllele>;
  leafForm: AllelePair<LeafFormAllele>;
  flowerForm: AllelePair<FlowerFormAllele>;
  primaryColor: AllelePair<PrimaryColorAllele>;
  secondaryColor: AllelePair<SecondaryColorAllele>;
  leafColor: AllelePair<LeafColorAllele>;
  pattern: AllelePair<PatternAllele>;
  size: AllelePair<SizeAllele>;
  aura: AllelePair<AuraAllele>;

  /**
   * НЕ локус. Копируется целиком от Seed Parent (delta doc §1 таблица,
   * §4.1) — фиксирует вид и body rig. Никогда не диплоиден, никогда не
   * участвует в mutation roll (§4.2 delta doc — жёсткое ограничение).
   */
  speciesId: number;

  /**
   * Результат ОТДЕЛЬНОГО mutation roll (§4.5.4), не значение локуса.
   * `null`, если в этом скрещивании не было mutation event. Один из шести
   * каталожных ID Gate 1 (delta doc §9): golden_vein / stardust / prism /
   * phoenix / double_bloom / luminous_edge.
   */
  mutationId: string | null;
}

type GenomeV2LocusKey =
  | 'stemForm' | 'leafForm' | 'flowerForm'
  | 'primaryColor' | 'secondaryColor' | 'leafColor'
  | 'pattern' | 'size' | 'aura';

/**
 * Раскрытые скрытые локусы конкретного экземпляра — единый контракт
 * видимости, `GENETICS_TARGET_DELTA.md` §6.1. JSON-сериализуемое хранение:
 * МАССИВ, не `Set` — `Set` не переживает `JSON.stringify`/`JSON.parse`
 * (превращается в `{}`), а весь save целиком сериализуется этим способом
 * (аудит §10.1). Порядок элементов массива не несёт смысла, дубликаты
 * логически не должны возникать (пишущий код обязан проверять наличие
 * перед добавлением), но само по себе поле — плоский массив записей.
 */
interface RevealedLocusEntry {
  locus: GenomeV2LocusKey;
  source: 'microscope' | 'natural';
}

/** Specimen — sidecar добавлен, legacy-поле `genome` не удаляется/не переписывается. */
interface Specimen {
  id: string;
  genome: Genome;                    // legacy, без изменений, аудит §2
  genomeV2?: GenomeV2;                // sidecar; undefined до backfill (delta doc §7.2)
  createdAt: number;
  favorite?: boolean;
  parentIds?: [string, string] | null;      // Slice 10, delta doc §12
  revealedLoci?: RevealedLocusEntry[];      // Slice 8, delta doc §6.1 — default: отсутствует/[]
}

/**
 * Persistence-only тип для содержимого Nursery Tray (`GENETICS_TARGET_DELTA.md`
 * §6). Только данные — никакой игровой логики (роста, разрешения фенотипа,
 * оплаты) на этом типе нет и не должно быть; вся логика живёт в
 * store/engine-коде, читающем и пишущем массив `HybridSeedV2[]`. Геном уже
 * полностью определён в момент скрещивания (delta doc §6, п.2) — до
 * созревания он просто не показывается игроку.
 */
interface HybridSeedV2 {
  id: string;
  genomeV2: GenomeV2;
  parentIds: [string, string];
  createdAt: number;
  plantedAt: number | null;   // null, пока семя лежит в трее, не посажено
  plotId: number | null;      // задаётся при посадке
}

// Расширение существующего GameState (остальные поля — без изменений):
interface GameState {
  // ...существующие поля не показаны...
  pollen: number;
  labLevel: number;
  nurseryTray: HybridSeedV2[];               // capacity 8
  firstBreedFreeClaimed: boolean;
  firstHybridRewardClaimed: boolean;
  firstRecycleTopUpClaimed: boolean;
}
```

## 4.2. Полный каталог аллелей Gate 1

Столбцы: стабильный ID, русское название, временное визуальное выражение (Gate 1 не имеет финального арта — placeholder-описание, art-pass отдельным проходом), dominance rank (1 = максимально доминантный в этом локусе — таблица полного доминирования, §4.3), вес появления (используется генератором случайного/базового генома — 0 означает «не входит в пул случайного рождения, достижим только наследованием от существующего носителя или через mutation roll», прямая аналогия с существующим прецедентом `aura:'radiant'` в legacy-коде, аудит §3.2: «`radiant` не входит в пул рождения, достижим только через мутацию/лок»), rarity points (вклад в `rarityOfV2`, §4.5), доступность Солнечнику/Колокольнику, допустимость межвидового наследования, участие в mutation pool, neutral migration ID (отмечен «да» для аллелей, используемых как нейтральный дефолт при миграции brand-new геометрических локусов — `GENETICS_TARGET_DELTA.md` §7 п.3).

Все 9 локусов доступны и Солнечнику, и Колокольнику одинаково в Gate 1 — видовых ограничений по аллелям в Gate 1 не вводится (упрощение первого прохода; видо-специфичные палитры — открытый вопрос будущих гейтов, не блокирует Gate 1). Межвидовое наследование разрешено для каждого аллеля каждого из девяти локусов без исключений — прямое следствие уже зафиксированного правила `GENETICS_TARGET_DELTA.md` §1 таблицы: «Все девять визуальных локусов... наследуются симметрично от обоих родителей тем же диплоидным механизмом»; исключение — только сам `speciesId`, который локусом не является (§4.1).

## 4.3. Доминирование

Gate 1 использует **исключительно полное доминирование**. Таблица выше (§4.2, столбец `Dominance rank`) **есть** сама `DOMINANCE_TABLE` — по одной явной записи на каждый аллель каждого локуса, без исключений и без `default`-ветки.

Алгоритм разрешения фенотипа (единственный, применяется одинаково ко всем девяти локусам):

```ts
function expressPhenotype<T extends string>(
  pair: AllelePair<T>,
  table: Record<T, { rank: number }>
): T {
  if (pair.a === pair.b) return pair.a;             // одинаковые аллели — выражаются напрямую
  return table[pair.a].rank < table[pair.b].rank ? pair.a : pair.b;   // меньший rank = более доминантный
}
```

Правила (все — прямые требования задания, здесь просто оформлены таблицей выше вместо прозы):

- у каждого локуса задан явный `rank` для **каждого** аллеля (§4.2) — таблица не содержит пропусков;
- более высокий приоритет (меньшее числовое значение `rank`) выражается у гетерозиготы;
- одинаковые аллели (гомозигота) выражаются напрямую, без обращения к рангу;
- **кодоминирование в Gate 1 не используется** — ни один локус, ни одна пара аллелей не имеет кодоминантной записи; `expressPhenotype()` всегда возвращает ровно один аллель, никогда «смешанное» значение;
- порядок полей `AllelePair.a`/`.b` не определяет доминирование неявно — единственный источник истины — числовой `rank` из таблицы; `a`/`b` — это только «от какого именно родителя пришёл этот конкретный аллель» (нужно для §6.1 delta doc — «происхождение признака»), не сигнал приоритета.

## 4.4. Полная legacy → V2 миграция (lossless mapping)

Применяется в рамках `ensureGenomeV2Sidecars` (`GENETICS_TARGET_DELTA.md` §7.2) к каждому specimen, у которого нет `genomeV2`. Все перечисленные ниже локусы **гомозиготны** после миграции (`locus.a = locus.b`, delta doc §7 п.1) — миграция никогда не создаёт скрытого состояния (delta doc §7 п.2).

| Legacy-поле | → | V2 | Правило |
|---|---|---|---|
| `genome.shape` (1-8) | → | `speciesId` + body rig | 1:1, прямое копирование числового значения; **не локус** — не диплоидное, гомозиготность неприменима (§4.1). |
| `genome.primary` (hex) | → | `primaryColor` (гомозиготно) | Точное совпадение hex→ID по таблице §4.2 (`primaryColor`). Каждый из 8 legacy hex имеет ровно один соответствующий V2 ID — маппинг биективен, ни одно значение не сводится к другому. |
| `genome.secondary` (hex) | → | `secondaryColor` (гомозиготно) | Точное совпадение hex→ID по таблице §4.2 (`secondaryColor`). Биективно на всех 7 legacy-значениях. |
| `genome.leaf` (hex) | → | `leafColor` (гомозиготно) | Точное совпадение hex→ID по таблице §4.2 (`leafColor`). Биективно на всех 3 legacy-значениях — это устраняет содержательный дефект 8-локусной модели (§0): цвет листа не теряется и не сливается с формой. |
| `genome.pattern` ∈ `{'solid','duotone'}` | → | `pattern` (гомозиготно) | `'solid'` → `pattern_solid`/`pattern_solid`; `'duotone'` → `pattern_duotone`/`pattern_duotone`. Точное 1:1 соответствие — ни `spots`/`stripes`/`veins` не участвуют в миграции ни при каких условиях (у них нет legacy-аналога). |
| `genome.size` ∈ `{'small','normal','large','giant'}` | → | `size` (гомозиготно) | Прямое совпадение по имени: `size_small`/`size_normal`/`size_large`/`size_giant` соответственно — гомозиготно на своём значении. |
| `genome.aura` ∈ `{'none','faint','glow','radiant'}` | → | `aura` (гомозиготно) | Прямое совпадение по имени: `aura_none`/`aura_faint`/`aura_glow`/`aura_radiant` соответственно — гомозиготно, **включая** `radiant` (мигрировавший specimen с `radiant` получает `aura_radiant`/`aura_radiant`, несмотря на то, что этот аллель не входит в пул случайного рождения V2 — ограничение пула касается только генерации новых геномов, не миграции существующих). |
| `genome.mutationId` | → | `genomeV2.mutationId` (копия, не переигранный ролл) | **Исправлено в проходе 6 — устраняет дефект прохода 5.** Один из четырёх Gate-1-каталожных legacy ID (`golden_vein`/`stardust`/`prism`/`phoenix`, аудит §4.4, `config.ts:73-78`) копируется **1:1** в `genomeV2.mutationId`. `null` мигрирует в `null`. Неизвестный/повреждённый ID (значение, не входящее в текущий каталог из четырёх legacy ID) не вызывает падения загрузки: `specimen.genome.mutationId` сохраняется без изменений (legacy-поле никогда не трогается, §4.1/delta doc §7 п.9), а `genomeV2.mutationId` в этом одном конкретном случае — `null` (безопасный дефолт для нераспознанного значения, не системная норма для известных ID). Копирование — это перенос уже состоявшегося исторического результата, не выдача новой мутации: миграция **не переигрывает** mutation roll и **не изменяет** `pityCounter` ни в одном из этих случаев (`ensureGenomeV2Sidecars` в принципе не читает и не пишет pity, §7.2 delta doc). **Почему это обязательно, не опционально**: если бы `genomeV2.mutationId` мигрировавшего мутировавшего specimen оставался `null` (как ошибочно требовала предыдущая редакция этой таблицы), будущий V2-рендер (читающий только `genomeV2`) визуально терял бы mutation-эффект и mutation rarity floor уже существующего мутировавшего растения — прямое нарушение требования «внешний вид legacy specimen не меняется» (delta doc §7 п.4) применительно к мутациям, не только к девяти локусам. |
| *(нет legacy-аналога)* | → | `stemForm = stem_standard`/`stem_standard` | Нейтральный дефолт, гомозиготно (delta doc §7 п.3). |
| *(нет legacy-аналога)* | → | `leafForm = leaf_standard`/`leaf_standard` | Нейтральный дефолт, гомозиготно — форма листа, не цвет (§0). |
| *(нет legacy-аналога)* | → | `flowerForm = flower_standard`/`flower_standard` | Нейтральный дефолт, гомозиготно (delta doc §7 п.3). |

**Гарантия «внешний вид legacy specimen не меняется» (delta doc §7 п.4)**: поскольку (а) все перенесённые локусы гомозиготны и, следовательно, экспрессия не зависит от `rank` (§4.3, первая ветка алгоритма), и (б) каждый ID→HEX/ID→enum маппинг выше точный и биективный на исходном множестве legacy-значений — рендер мигрировавшего specimen по `genomeV2` обязан визуально совпадать с рендером по старому `genome` для всех перенесённых полей. Три новых локуса (`stemForm`/`leafForm`/`flowerForm`) не имеют legacy-визуального аналога вообще — их нейтральный дефолт обязан ссылаться на art-ассет, максимально близкий к «нейтральному» текущему силуэту (техническая привязка ID→ассет — задача art-pass, delta doc §11 п.5, не продуктовое решение).

Ни одно старое значение не отбрасывается молча и не сводится к другому цвету — каждый из 8+7+3 legacy цветовых hex явно перечислен в §4.2 под собственным семантическим ID, и migration mapping выше ссылается на них по точному совпадению, не по приближению.

## 4.5. Точная rarity-модель

### 4.5.1. Формула

```ts
function rarityOfV2(genomeV2: GenomeV2, mutationId: string | null): RarityTier {
  const naturalScore = sumOf(NINE_LOCI, locus =>
    RARITY_POINTS[locus][expressPhenotype(genomeV2[locus], DOMINANCE_TABLE[locus])]
  );

  const naturalTier = tierFromScore(naturalScore);   // §4.5.2, без учёта мутации

  if (mutationId === null) return naturalTier;

  const mutationTier = MUTATION_CATALOG[mutationId].tier;      // Minor/Major/Signature, delta doc §9
  const floor = { Minor: 'Rare', Major: 'Epic', Signature: 'Legendary' }[mutationTier];
  let tier = higherOf(naturalTier, floor);                      // §4.5.2 — «выше» = дальше по списку тиров

  if (mutationTier === 'Signature' && naturalScore >= MYTHIC_CO_THRESHOLD) {
    tier = 'Mythic';
  }
  return tier;
}
```

- **Редкость следует из выраженного генома** — `rarityOfV2` не содержит собственного случайного вызова: единственная случайность во всей цепочке — уже произошедший mutation roll (§4.5.4), результат которого (`mutationId`) передаётся сюда как аргумент. Никакого дополнительного rarity-roll нет.
- `naturalScore` — целочисленная сумма `rarity points` (§4.2) **выраженных** (после разрешения доминирования, §4.3) аллелей по всем девяти локусам. Диапазон в Gate-1-каталоге — 0…29 (сумма максимальных points каждого локуса: 5+4+4+4+4+2+5+3+5=29), фактически наблюдаемый максимум в популяционной симуляции — 14 (§4.5.5, распределение соответствует случайно рождённой/скрещённой популяции, не теоретическому максимуму, который требует одновременного совпадения самых редких аллелей всех девяти локусов сразу).

### 4.5.2. Пороги (natural score → tier, без учёта мутации)

| Tier | Условие по `naturalScore` |
|---|---|
| Common | `< 3` |
| Uncommon | `3 ≤ score < 6` |
| Rare | `6 ≤ score < 8` |
| Epic | `8 ≤ score < 10` |
| Legendary | `score ≥ 10` |
| Mythic | **не достижим через `naturalScore` в одиночку** — только через mutation floor (ниже) |

`tierFromScore()` возвращает один из первых пяти тиров (Common…Legendary) — Mythic не входит в её область значений: это прямое следствие того, что в исходном GDD v3 Mythic описан не как результат самой сильной комбинации обычного наследования, а как результат **сочетания** Signature-мутации и редкого генома (§6.3 GDD v3: *«Mythic возникает не как покупаемый джекпот, а когда Signature-мутация сочетается с редким совместимым геномом»*) — формула выше кодирует это буквально: Mythic достижим только через отдельную ветку `mutationTier === 'Signature' && naturalScore >= MYTHIC_CO_THRESHOLD`.

### 4.5.3. Mutation floors

| Tier мутации (delta doc §9, GDD v3 §6.3) | Минимальная итоговая редкость |
|---|---|
| Minor | ≥ Rare |
| Major | ≥ Epic |
| Signature | ≥ Legendary |

`higherOf(naturalTier, floor)` берёт более редкий из двух — если `naturalScore` уже случайно попал выше пола (например, Major-мутация выпала на генетически уже-Legendary особи), итог остаётся на более высоком натуральном уровне, floor его не занижает.

### 4.5.4. Mythic — отдельное явно записанное условие

```
MYTHIC_CO_THRESHOLD = 5
```

Mythic присваивается **только** когда одновременно: (а) mutation roll выбрал tier `Signature` **и** (б) `naturalScore` этого конкретного генома (то есть редкость, которую геном имел бы и без мутации) не ниже `MYTHIC_CO_THRESHOLD=5`. И Minor-, и Major-мутации, при сколь угодно высоком `naturalScore`, никогда не дают Mythic — их floor заканчивается на Rare/Epic соответственно, `higherOf` может поднять их итог максимум до Legendary (если натуральный score уже там), но ветка Mythic в формуле условлена явно на `mutationTier === 'Signature'` и нигде больше. Это единственное условие Mythic во всей модели — не эвристика, не «очень редкое совпадение может засчитаться», а явная проверка двух конкретных предикатов.

### 4.5.6. Известное упрощение Gate 1 — mutation pool сосредоточен в одном локусе

В этом первом каталоге единственный аллель с `mutation pool = да` — `aura_radiant` (§4.2). Это значит, что в текущей калибровке **любой** успешный mutation roll (Minor/Major/Signature) механически проявляется как «новый редкий аллель локуса ауры» — прямое, но узкое прочтение GDD v3 §6.3 («новый редкий аллель одного обычного локуса» для Minor). Это сознательное упрощение первого прохода, не архитектурное ограничение: `mutation pool = да` — обычный столбец каталога (§4.2), и добавление mutation-only аллелей в другие локусы (например, `pattern_veins` или `primary_frost`, уже самые редкие в своих locus) — работа калибровки (Slice 13), не требующая изменения схемы данных или алгоритма `rarityOfV2`.

### 4.6.3. Первое скрещивание — seed RNG и точный геном ребёнка

**Seed**: `mulberry32(20260828)`. ### 4.6.4. Второе обучающее скрещивание — родители, seed, гарантированное раскрытие

Родители — те же два стартовых Солнечника (§4.6.1/§4.6.2), доступны повторно (в Gate 1 родители не расходуются при скрещивании, аудит §8, `store.ts:268-271`).

**Seed**: отдельный поток (второе скрещивание — отдельный вызов `breedV2`, `pityCounter` уже равен 1 после первого скрещивания — порог mutation roll для второй попытки 4%, delta doc §4.2). Seed для этого скрещивания выбирается так, что: (а) mutation roll не срабатывает (тот же принцип, что и в §4.6.3 — конкретное числовое значение потока фиксируется на этапе реализации Slice 12 вместе с реальным RNG call order, `GENETICS_TARGET_DELTA.md` §11 п.5 — этот документ фиксирует **обязательные свойства** seed, не байт-в-байт значение несуществующего пока кода, тот же принцип уже используется в `GENETICS_ONBOARDING_SPEC.md` §3.2); (б) на локусе `size` коинфлип выбирает скрытый `size_large` **от обоих** родителей.

Все остальные восемь локусов наследуются идентично первому скрещиванию (родители не изменились) — единственное отличие результата от §4.6.3 сосредоточено в локусе `size`.

| Локус | Пара у ребёнка | Выражено |
|---|---|---|
| `size` | `size_large`/`size_large` | **`size_large`** |
| *(остальные восемь локусов)* | те же пары, что в §4.6.3 | те же значения, что в §4.6.3 |

**Какой скрытый аллель гарантированно проявляется**: `size_large` (Крупный) — оба родителя визуально показывают «Обычный» размер (`size_normal`, доминантный над скрытым у обоих), но потомок гомозиготен по `size_large` (получает его от **обоих** родителей одновременно) и потому выражает его напрямую (§4.3, первая ветка алгоритма — одинаковые аллели выражаются без обращения к рангу). Это прямой пример «естественного раскрытия» (`GENETICS_TARGET_DELTA.md` §6.1): после этого Reveal локус `size` у **обоих** родителей считается раскрытым естественным путём (их расширенная карточка перестаёт показывать «Не исследован» для этого локуса).

**Итоговая редкость этого скрещивания** (для полноты, не заявлена онбордингом как гарантированная величина, но детерминированно следует из фиксированных родителей+seed): `naturalScore = 0+0+1+1+1+1(size_large)+1+0+0 = 5` → `3 ≤ 5 < 6` → Uncommon (тот же тир, что и первое скрещивание — совпадение конкретно этой пары фикстур, не заложенное как отдельное требование онбординга).

**Изменение pity после каждого скрещивания**: `pityCounter` стартует на `0`. После первого скрещивания (§4.6.3, без мутации) → `pityCounter=1`. После второго скрещивания (§4.6.4, без мутации) → `pityCounter=2`. Совпадает буквально с `GENETICS_TARGET_DELTA.md` §6.3: «после первых двух обучающих скрещиваний `pityCounter=2`».
