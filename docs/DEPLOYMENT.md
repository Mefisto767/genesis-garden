# Genesis Garden — деплой и CI/CD

## Обзор пайплайна

Единственный workflow — `.github/workflows/ci.yml`, два job'а:

1. **`test`** — запускается на каждый push в `main` и на каждый pull request:
   - `npm ci` в `apps/web`
   - lint (`npm run lint`, oxlint)
   - typecheck (`npx tsc -b --noEmit`)
   - юнит-тесты (`npx vitest run`)
   - SQL/RLS/RPC-тесты против настоящего `postgres:16` service-контейнера (`supabase/tests/run_ci.sh` — тот же набор миграций и assertions, что `run_local.sh` в песочнице разработки, только TCP+пароль вместо `su postgres`)
   - продакшн-сборка (`npm run build`)
   - установка Playwright-браузеров (`npx playwright install --with-deps chromium`) и всех трёх e2e-скриптов (`test-e2e.mjs`, `test-e2e-genetics.mjs`, `test-e2e-newuser-journey.mjs`) поверх поднятого `vite preview`
   - скриншоты каждого прогона загружаются как build-artifact (`e2e-screenshots`) независимо от результата — для отладки упавшего прогона без доступа к самому раннеру
2. **`deploy`** — запускается только если `test` прошёл зелёным **и** это `push` именно в `main` (не PR, не другая ветка):
   - скачивает `dist/`, собранный job'ом `test`
   - публикует его в ветку `gh-pages` через `peaceiris/actions-gh-pages@v3` (используется `secrets.GITHUB_TOKEN`, отдельный PAT не нужен — стандартный токен Actions с правом `contents: write` на этот репозиторий достаточен)
   - `force_orphan: true` — история `gh-pages` не нужна, каждый деплой это чистый снимок билда, а не накопление коммитов
   - после публикации — smoke-test: до 6 попыток `curl` на `https://mefisto767.github.io/genesis-garden/` с паузой 20с между попытками (Pages может обновляться не мгновенно), job падает, если сайт так и не ответил

## Требуемые секреты

**Ни один шаг не требует секретов сборки.** Ни `test`, ни `deploy` не используют `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`/`VITE_PAYMENTS_*`/`VITE_SENTRY_DSN` — сборка для беты сознательно идёт без них (см. `apps/web/.env.example`: все облачные фичи выключены по умолчанию, `VITE_CLOUD_SYNC_ENABLED=false`, `VITE_PAYMENTS_ENABLED=false`). Это не забытый шаг, а прямое следствие текущей стадии: приложение полностью работоспособно как локальная игра без единого внешнего ключа.

`deploy` использует только встроенный `secrets.GITHUB_TOKEN`, который GitHub Actions создаёт автоматически для каждого прогона — никакой ручной настройки секретов в репозитории на данный момент не требуется.

Если владелец решит собирать бету с реальными облачными ключами по умолчанию (не рекомендуется, пока Supabase-проект/Paddle-аккаунт не проверены вручную — см. `docs/PAYMENTS.md`), это отдельное осознанное решение: тогда значения нужно завести как repo secrets (Settings → Secrets and variables → Actions) и явно прокинуть их в шаг `Build` через `env:` — сейчас в workflow этого нет намеренно.

## Как запускается деплой

Автоматически — при каждом push в `main` после того, как `test` прошёл. Ручной запуск возможен через `workflow_dispatch` (кнопка "Run workflow" на вкладке Actions в GitHub) — например, чтобы передеплоить без нового коммита.

## Честная оговорка: не проверено вживую

Эта сессия разработки не имеет push-доступа к `Mefisto767/genesis-garden` (нет PAT/`gh auth` — см. `docs/IMPLEMENTATION_STATUS.md`, открытые вопросы владельцу), поэтому сам workflow ни разу не выполнялся настоящим GitHub Actions раннером. Что реально проверено в песочнице разработки перед тем, как довериться каждому шагу:

- YAML синтаксически валиден (`python3 -c "import yaml; yaml.safe_load(...)"`);
- та же последовательность команд (`npm ci` → lint → typecheck → vitest → SQL-тесты → build → e2e) реально выполнялась в песочнице много раз на протяжении всех 11 этапов — просто не через сам файл `ci.yml`, а вручную теми же командами;
- `supabase/tests/run_ci.sh` (TCP-вариант SQL-тестов для CI) отдельно запущен и сверен с `run_local.sh` — установлен реальный пароль на локальный Postgres, подтверждено, что все те же assertions проходят по TCP так же, как через `su postgres`;
- три e2e-скрипта переведены на портируемый импорт `playwright` (через новый корневой `package.json`) и conditional `executablePath` — так, чтобы работать без изменений и в песочнице, и в CI, где Chromium ставится через `npx playwright install --with-deps chromium`, а не лежит в фиксированном пути.

Что **не** проверено и не может быть проверено без живого раннера: поведение `actions/*`-экшенов конкретных версий на инфраструктуре GitHub, реальное время выполнения job'ов, доступность `postgres:16`-сервиса именно в GitHub-раннерах (публичный образ, должен работать как везде, но не запущен там лично), фактическая публикация в `gh-pages` и то, что smoke-test действительно увидит обновлённый сайт. Первый реальный прогон после push будет первой настоящей проверкой всего файла целиком — если он упадёт на шаге, недоступном в песочнице, это будет видно в логах Actions и потребует точечного фикса, а не пересборки пайплайна с нуля.

## Ручной деплой без push-доступа (использовалось для v0.4)

До готовности этого пайплайна на GitHub уже опубликована ветка `gh-pages` с более старой версией (v0.4-genetics, без этапов 2–9 текущего техрегламента) — она была задеплоена вручную через PAT владельца в отдельной сессии, командами, эквивалентными тому, что теперь делает job `deploy`:

```bash
cd apps/web && npm run build
npx gh-pages -d dist -r https://<PAT>@github.com/Mefisto767/genesis-garden.git
```

Этот способ остаётся рабочим fallback'ом, если по каким-то причинам сам workflow временно недоступен, но с готовым `ci.yml` предпочтительный путь — обычный push в `main` после ревью PR: тесты и деплой проходят автоматически и одинаково от раза к разу, без риска забыть шаг или задеплоить непротестированный билд.

## Что нужно от владельца, чтобы это заработало на реальном GitHub

1. Запушить содержимое этой ветки/патча в `Mefisto767/genesis-garden` (см. `docs/IMPLEMENTATION_STATUS.md` — открытый пункт про push-доступ; сессия разработки не может сделать это сама).
2. На вкладке Settings → Pages репозитория убедиться, что источником публикации выбрана ветка `gh-pages` (root) — `peaceiris/actions-gh-pages` создаст её при первом успешном прогоне `deploy`, если она отсутствует, но настройку источника Pages GitHub не выставляет автоматически при самом первом запуске — это нужно проверить один раз вручную после первого прогона.
3. Дальше — ничего: каждый следующий push в `main` (например, через смерженный PR) будет тестироваться и деплоиться сам.
